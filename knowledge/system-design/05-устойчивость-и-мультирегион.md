# Устойчивость, радиус поражения и мультирегион

## Базовый принцип

**Отказы неизбежны. Проектируется не их отсутствие, а ограничение последствий и предсказуемость поведения.** Вопрос не «сломается ли», а «сколько пользователей задело, за сколько восстановились, что при этом продолжало работать».

---

## Радиус поражения (blast radius)

Для каждого отказа посчитай, сколько пользователей он задевает:

| Отказ | Радиус в наивной архитектуре | Радиус при изоляции |
|---|---|---|
| один экземпляр сервиса | 0 при N > 1 и корректном health-check | 0 |
| одна зона доступности | **все пользователи** (при перекрёстных вызовах) | 1/N при ячеистой топологии |
| один шард БД | все пользователи шарда | те же, но с деградацией вместо отказа |
| отравленный запрос (poison pill) | **все** | одна ячейка |
| плохой деплой | **все** | канарейка + одна ячейка |
| исчерпание общего ресурса (пул соединений, квота) | **все** | один отсек (bulkhead) |

**Задача архитектора — сделать так, чтобы ни один отказ не имел радиуса «все».**

## Cell-based architecture (ячеистая архитектура)

Подход, которым AWS строит свои сервисы более десяти лет; развитие идеи bulkhead из столпа надёжности Well-Architected.

**Ячейка** — полный, самодостаточный экземпляр системы: свои прикладные сервисы, своя база, свой кэш. Ячейка обслуживает подмножество пользователей и **не обращается к компонентам других ячеек**. Отказ ячейки задевает только её пользователей.

**Маршрутизатор ячеек (cell router)** — тонкий слой, определяющий по ключу (арендатор, пользователь, регион), в какую ячейку направить запрос. Это единственный общий компонент, поэтому он обязан быть максимально простым и надёжным: **вся сложность внутри ячеек, маршрутизатор только считает функцию от ключа**.

**Размер ячейки** выбирается из двух соображений: достаточно мала, чтобы её отказ был приемлем и чтобы её можно было целиком протестировать; достаточно велика, чтобы накладные расходы на ячейку окупались. На практике — доля процентов от общей нагрузки на ячейку.

**Что даёт:**
- отказ ограничен ячейкой;
- выкат идёт ячейка за ячейкой — плохой релиз задевает малую долю;
- ячейка целиком тестируема и воспроизводима;
- нагрузочные характеристики предсказуемы: масштабирование = добавление ячеек, а не рост существующих.

**Чем платим:** дублирование инфраструктуры, сложность маршрутизации и переезда между ячейками, невозможность дешёвых кросс-ячеечных запросов, рост эксплуатационной нагрузки.

> **Slack пришёл к ячейкам после инцидента 30 июня 2021**, когда отказ сетевого канала в одной зоне доступности вызвал видимый пользователям сбой: сервисы были распределены по зонам, но ходили друг к другу через границы зон, поэтому «серый» отказ одной зоны растёкся по всем. В их модели ячейка = зона доступности, сервисы внутри зоны общаются только между собой, а слив трафика делается на пограничных балансировщиках перевешиванием весов кластеров с шагом 1%. Подробнее — в `case-studies/`.

## Shuffle sharding

Развитие ячеек. Вместо назначения клиента одной ячейке ему назначается **случайная комбинация** из нескольких узлов. При N узлах и комбинациях по 2 число уникальных комбинаций растёт квадратично, поэтому вероятность, что два клиента получат одинаковый набор, мала.

**Эффект:** отравленный запрос или злоупотребление со стороны одного клиента задевает только тех, кто делит с ним оба узла, — доли процента, а не всех. При 8 узлах и наборах по 2 отказ пары задевает ~1,8% комбинаций.

**Где применять:** мультиарендные системы, API-шлюзы, очереди задач — везде, где один клиент может испортить жизнь остальным.

## Паттерны стабильности

| Паттерн | Что делает | Обязателен когда |
|---|---|---|
| **Timeout** | ограничивает ожидание | **всегда, на каждом сетевом вызове.** Отсутствие таймаута — дефект |
| **Retry с ограничением** | повтор при временной ошибке | только для идемпотентных операций; обязательно с потолком попыток и экспоненциальной задержкой с джиттером |
| **Circuit breaker** | перестаёт ходить в нездоровую зависимость, быстро возвращает ошибку или фолбэк | при синхронных вызовах внешних систем |
| **Bulkhead** | изолирует ресурсы (пулы, очереди, потоки) по типам нагрузки | когда одна нагрузка может исчерпать общий пул |
| **Backpressure** | честно отказывает на входе вместо роста очереди | всегда на границе системы |
| **Load shedding** | сбрасывает низкоприоритетный трафик при перегрузке | когда есть приоритеты запросов |
| **Rate limiting** | ограничивает клиента | на публичных API. Алгоритмы: token bucket (допускает всплеск), leaky bucket (ровный поток), sliding window (точнее fixed window на границах окон) |
| **Deadline propagation** | сквозной срок жизни запроса передаётся по цепочке | в цепочках длиннее двух звеньев — не тратить ресурсы на заведомо просроченное |
| **Graceful degradation** | часть функций отключается, ядро работает | по каждой некритичной зависимости |
| **Fail fast** | немедленный отказ при заведомо невыполнимом запросе | при исчерпанных ресурсах, невалидном входе |
| **Static stability** | система переживает отказ управляющего слоя, продолжая работать на последней известной конфигурации | для критичных сервисов; **не делай data plane зависимым от доступности control plane** |

### Шторм повторных запросов

Ретраи на нескольких слоях перемножаются: три попытки на трёх уровнях = 27 запросов вместо одного. Признаки: p50 не меняется, p95–p99 улетают, CPU скачет при неизменном бизнес-трафике.

**Правила:**
1. Ретраит **ровно один слой** в цепочке; остальные пробрасывают ошибку. Назначь его явно и запиши в документ.
2. Потолок попыток и общий бюджет времени.
3. Экспоненциальная задержка **с джиттером** — без джиттера повторы синхронизируются и бьют залпом.
4. **Retry budget** — доля повторов от общего трафика ограничена (например, 10%); превысили — перестаём ретраить.

### Борьба с хвостами задержек

- **Hedged requests** — если запрос не уложился в p95, шлём вторую копию на другую реплику и берём первый ответ. **Только для идемпотентных операций.**
- **Tied requests** — копии на два узла с общим идентификатором; кто взял в работу, отменяет копию.
- **Latency-aware балансировка** — отправлять на узлы с исторически **меньшей** задержкой, давая отдохнуть деградировавшим.
- **Request coalescing** — склейка одинаковых одновременных запросов.
- **Джиттер фоновых задач** — размазать по времени вместо залпа в ровный час.

## Мультирегион

### Сначала честный вопрос

Мультирегион удорожает всё: задержку, стоимость, сложность разработки, эксплуатацию. **Если продукт переживает 1–2 часа простоя раз в год, мультирегион с синхронными кворумами — избыточное усложнение.** Решение принимается от RPO/RTO и требований резидентности, а не от желания «как у гигантов».

### Топологии

| Топология | RPO | RTO | Стоимость | Сложность |
|---|---|---|---|---|
| **Один регион, несколько зон** | ~0 внутри региона | минуты | базовая | низкая |
| **Active-passive, холодный резерв** | часы | часы | +10–20% | низкая |
| **Active-passive, тёплый резерв** | минуты | десятки минут | +40–60% | средняя |
| **Active-active по регионам, данные разделены по регионам** | ~0 для своего региона | минуты | ×2 | высокая |
| **Active-active с общими данными** | зависит от репликации | минуты | ×2+ | **очень высокая** — конфликты записи |

**Ключевое упрощение: разделяй данные по регионам (region-partitioned).** Если пользователь принадлежит региону и его данные живут только там, active-active получается без конфликтов записи. Это же обычно совпадает с требованиями резидентности. Сложность возникает только там, где нужны глобально согласованные данные.

### Что нужно решить явно

- **Маршрутизация пользователя:** GeoDNS (просто, но кэшируется у резолверов), anycast (быстрое переключение, требует поддержки сети), latency-based routing.
- **Глобально уникальные идентификаторы:** автоинкремент невозможен. Snowflake-подобные ID (время + идентификатор узла + счётчик), UUIDv7 (сортируемый по времени), ULID.
- **Данные, которые обязаны быть глобальными:** учётные записи, справочники, конфигурация. Обычно read-heavy — реплицируются во все регионы, пишутся в один.
- **Конфликты:** если запись возможна в двух регионах — механизм разрешения обязателен и обязан быть описан (LWW, версионные векторы, CRDT, разведение по ключу).
- **Failover:** автоматический или ручной, кто принимает решение, как проверяется, что резерв жив. **Непроверенный failover не существует.**
- **Резидентность:** какие данные не покидают юрисдикцию; как это обеспечивается в бэкапах, логах и трассировках — **утечка ПДн в централизованные логи типовая ошибка**.

### Уровни готовности к катастрофе

1. **Бэкап и восстановление** — RPO часы, RTO часы-сутки. Дёшево.
2. **Pilot light** — минимальный набор запущен в резервном регионе, данные реплицируются. RTO десятки минут.
3. **Warm standby** — уменьшенная копия работает и принимает часть трафика. RTO минуты.
4. **Multi-site active-active** — полноценные регионы. RTO секунды-минуты, максимальная стоимость.

**Обязательно:** регулярное учебное переключение. Восстановление, которое ни разу не проверяли, при аварии не сработает.

## Геопространственные данные

Для сервисов с картой, поиском поблизости и зонами.

- **Geohash** — строковый префиксный код; удобно индексировать в обычной БД, но соседние ячейки могут иметь непохожие префиксы (проблема границ).
- **H3** (Uber) — иерархическая гексагональная сетка, 16 уровней разрешения. **Гексагоны дают единое расстояние до всех соседей**, в отличие от квадратов (два разных расстояния) и треугольников (три), что упрощает анализ и сглаживание. Идентификатор потомка усекается до предка — эффективная иерархия. Применяется для расчёта спроса и предложения по зонам, динамического ценообразования, диспетчеризации.
- **S2** (Google) — иерархические ячейки на сфере, кривая Гильберта; хорошая локальность.
- **PostGIS / R-tree** — точные геометрические запросы, когда нужна геометрия, а не сетка.

**Правило выбора:** нужна агрегация и аналитика по зонам — сетка (H3/S2). Нужны точные полигоны и расстояния — PostGIS.

## Наблюдаемость как часть архитектуры

**Компонент без метрик и трассировки считается непроектированным.**

- **Три сигнала:** метрики (агрегаты), логи (события), трассировки (путь запроса). Стандарт сбора — OpenTelemetry.
- **RED** для сервисов: Rate, Errors, Duration. **USE** для ресурсов: Utilization, Saturation, Errors.
- **Сквозной идентификатор запроса** через все компоненты — единственный способ понять, какое звено даёт хвост.
- **SLI/SLO/бюджет ошибок:** SLI — измеряемая доля успешных взаимодействий; SLO — цель; бюджет ошибок — допустимый остаток. **Исчерпан бюджет — останавливаются функциональные релизы в пользу надёжности.** Это управленческий механизм, а не только метрика.
- **Алерты — на симптомы, а не на причины.** Алерт «CPU 90%» бесполезен; алерт «p99 оформления заказа вышел за SLO на 5 минут» — действие.
- **Кардинальность меток** — типовая причина, по которой падает система мониторинга. Не класть в метки идентификаторы пользователей.
