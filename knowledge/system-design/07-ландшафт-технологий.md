# Ландшафт технологий

Что существует в мире и **по какому признаку выбирать**. Конкретный продукт выбирается только после ответа на вопросы платформы (шаг 0 процесса): в закрытом контуре недоступны управляемые сервисы облаков, в компании может быть реестр одобренного ПО.

**Главное правило выбора: технология, которую некому эксплуатировать, — не вариант.** Экспертиза команды весит больше, чем технические достоинства.

---

## Хранилища данных

### Реляционные (OLTP)
**PostgreSQL** — умолчание для подавляющего большинства задач. ACID, богатый SQL, расширения (PostGIS для гео, pgvector для векторов, TimescaleDB для временных рядов), логическая репликация. **Начинай отсюда, пока не доказано, что не подходит.**
**MySQL / MariaDB** — там, где есть экспертиза; экосистема Vitess для горизонтального шардирования.
**Российские:** Postgres Pro, Tantor — форки PostgreSQL с поддержкой и сертификацией.
**Распределённые SQL (NewSQL):** CockroachDB, YugabyteDB, TiDB, YDB — горизонтальное масштабирование с сохранением SQL и транзакций. Цена — задержка на консенсус и эксплуатационная сложность. Google Spanner — эталон, но привязан к GCP.

### Ключ-значение и кэш
**Redis / Valkey** — кэш, сессии, счётчики, лидерборды, простые очереди, распределённые блокировки. Однопоточная модель команд; кластер для шардирования.
**Memcached** — проще Redis, только кэш.
**etcd, Consul, ZooKeeper** — не кэш, а согласованное хранилище конфигурации и координации на консенсусе. Для service discovery, выбора лидера, распределённых блокировок.

### Широко-колоночные и распределённые
**Cassandra / ScyllaDB** — огромный объём, высокая скорость записи, линейное масштабирование, отсутствие единой точки отказа. Нет джойнов, модель данных проектируется под запросы. **ScyllaDB** — переписанная на C++ Cassandra без пауз сборщика мусора; типичный сценарий миграции для тех, кто упёрся в JVM-паузы.
**HBase** — экосистема Hadoop.

### Документные
**MongoDB** — гибкая схема, быстрый старт, горизонтальное шардирование. Риск: отсутствие схемы перекладывает согласованность на приложение.
**Couchbase, DocumentDB** — альтернативы.

### Колоночные (OLAP)
**ClickHouse** — очень быстрые аналитические запросы, сжатие, потоковая вставка. Умолчание для аналитики и дашбордов в России и не только.
**Apache Druid, Apache Pinot** — аналитика в реальном времени с низкой задержкой запроса.
**Greenplum, Vertica, Snowflake, BigQuery** — хранилища данных.

### Временные ряды
**TimescaleDB** (расширение Postgres), **VictoriaMetrics**, **InfluxDB**, **Prometheus TSDB** — метрики, телеметрия, IoT.

### Поиск
**Elasticsearch / OpenSearch** — полнотекстовый поиск, агрегации, логи. **Не источник правды** — индекс, наполняемый из основного хранилища.
**Meilisearch, Typesense** — легче, для продуктового поиска среднего масштаба.
**Manticore, Sphinx** — альтернативы.

### Векторные
**pgvector** (в PostgreSQL), **Qdrant**, **Milvus**, **Weaviate** — семантический поиск, RAG. Для умеренных объёмов pgvector избавляет от отдельной системы.

### Графовые
**Neo4j**, **JanusGraph**, **ArangoDB** — когда связи важнее сущностей: рекомендации, антифрод, графы доступа. При простых иерархиях достаточно рекурсивных CTE в Postgres.

### Объектные
**S3** и совместимые: **MinIO**, **Ceph RGW**, Yandex Object Storage. Медиа, бэкапы, датасеты, статика. **Не хранить файлы в БД и на диске приложения.**

## Обмен сообщениями

**Apache Kafka** — распределённый лог. Событийная архитектура, CDC, потоковая аналитика. Порядок в партиции, перечитывание, несколько групп потребителей.
**RabbitMQ** — брокер очередей. Гибкая маршрутизация, приоритеты, DLQ. Для распределения задач.
**NATS / NATS JetStream** — лёгкий, низкая задержка, простая эксплуатация.
**Apache Pulsar** — лог с многоарендностью и разделением хранения и вычислений.
**Redpanda** — Kafka-совместимый на C++, без JVM.
**Debezium** — CDC из БД в Kafka; штатный способ реализовать outbox без изменения приложения.
**Apache Flink, Kafka Streams** — потоковая обработка с состоянием, оконные агрегации.

## Сеть и доставка трафика

**Обратные прокси и балансировщики:** Nginx, HAProxy, Envoy, Traefik. **Envoy** — основа большинства современных service mesh, поддерживает динамическую конфигурацию, взвешенные кластеры (именно этим Slack сливает трафик между ячейками), продвинутые политики.
**API-шлюзы:** Kong, APISIX, Tyk, Gravitee, Envoy Gateway. Аутентификация, лимиты, маршрутизация, агрегация.
**Service mesh:** Istio, Linkerd, Cilium Service Mesh. mTLS между сервисами, повторы и таймауты на уровне инфраструктуры, наблюдаемость без изменения кода. **Оправдан при десятках сервисов; для пяти — избыточен.**
**CDN:** Cloudflare, Akamai, Fastly, CloudFront, Yandex CDN, EdgeЦентр. Для собственного контура — Varnish, ATS, Nginx с кэшем.
**DNS и глобальная маршрутизация:** GeoDNS, anycast, latency-based routing.

## Выполнение и оркестрация

**Kubernetes** — де-факто стандарт. Дистрибутивы: ванильный, OpenShift, Rancher, Deckhouse, Astra Managed Kubernetes.
**Nomad** — проще Kubernetes, если не нужна его экосистема.
**Serverless:** AWS Lambda, Cloud Functions, Yandex Cloud Functions, Knative для своего контура.
**Автомасштабирование:** HPA, VPA, KEDA (по длине очереди и внешним метрикам), Cluster Autoscaler. **Помни про cold start — расширение не мгновенно.**

## Инфраструктура как код и доставка

**Terraform / OpenTofu, Pulumi, Crossplane** — описание инфраструктуры.
**Ansible, SaltStack** — конфигурация серверов.
**Helm, Kustomize** — пакетирование для Kubernetes.
**ArgoCD, Flux** — GitOps: состояние кластера — производная от git.
**GitLab CI, GitHub Actions, Jenkins, TeamCity, Woodpecker** — конвейеры.
**Стратегии выката:** rolling, blue-green, canary, feature flags (Unleash, Flagsmith, LaunchDarkly).

## Наблюдаемость

**Сбор:** OpenTelemetry — стандарт, к которому стоит приводить всё новое.
**Метрики:** Prometheus, VictoriaMetrics (лучше держит большие объёмы), Thanos/Mimir для долгого хранения.
**Логи:** Loki (дёшево, по меткам), ELK/OpenSearch (полнотекстовый поиск, дороже), Vector как агент.
**Трассировки:** Jaeger, Tempo, Zipkin.
**Визуализация и алерты:** Grafana, Alertmanager.
**Ошибки приложения:** Sentry, GlitchTip.
**Профилирование в проде:** Pyroscope, Parca.

## Безопасность

**Секреты:** HashiCorp Vault, OpenBao, Sealed Secrets, External Secrets Operator. **Секреты не в git и не в переменных окружения открытым текстом.**
**Идентификация:** Keycloak, Authentik, Ory, корпоративный SSO. Протоколы: OAuth 2.1, OIDC, SAML.
**Управление доступом:** RBAC, ABAC; политики — OPA/Gatekeeper, Kyverno.
**Сеть:** mTLS (через mesh или напрямую), network policies, сегментация.
**Сканирование:** Trivy, Grype (образы и зависимости), SAST-инструменты, Dependency-Track.
**Моделирование угроз:** STRIDE, OWASP Threat Dragon.

## Как выбирать: практические правила

1. **Начинай с PostgreSQL + Redis + объектное хранилище.** Эта тройка закрывает большинство задач до заметного масштаба. Расширять — только когда конкретное требование доказано не выполняется.
2. **Одна технология на один класс задач.** Два брокера, три СУБД одного типа, четыре языка — умножение эксплуатационной нагрузки без выигрыша.
3. **Управляемый сервис против self-hosted:** управляемый почти всегда дешевле по совокупной стоимости, если политика позволяет. В закрытом контуре считай стоимость эксплуатации честно — она обычно превышает стоимость лицензий.
4. **Зрелость и сообщество важнее возможностей.** Технология, у которой некому задать вопрос, обходится дороже.
5. **Проверь путь выхода.** Как мигрировать прочь, если не подойдёт. Отсутствие ответа — риск, который надо записать.
6. **Экзотика требует ADR с обоснованием**, почему стандартное решение не подходит.
