# Числа и оценка порядка величин

Все числа — **ориентиры для прикидки порядка**, а не спецификации железа. Проверены по открытым источникам в августе 2026; сильно зависят от конкретного оборудования, нагрузки и настроек.

---

## Задержки

| Операция | Порядок |
|---|---|
| Обращение к L1-кэшу процессора | ~1 нс |
| Обращение к L2 | ~4 нс |
| Блокировка/разблокировка мьютекса | ~20 нс |
| Обращение к оперативной памяти | ~100 нс |
| Round trip до GPU или NIC по PCIe | ~200 нс |
| Сжатие 1 КБ | ~2 мкс |
| Случайное чтение с NVMe | **15–70 мкс** |
| Случайное чтение с SATA SSD | 100–200 мкс |
| Чтение 1 МБ последовательно из памяти | ~50 мкс |
| Round trip внутри дата-центра | **~500 мкс** |
| Чтение 1 МБ последовательно с NVMe | ~200 мкс |
| NVMe over TCP: добавка сети | 250–450 мкс, итого 300–500 мкс |
| Случайное чтение с HDD (seek) | **5–10 мс** |
| Round trip Москва — Петербург | ~10–15 мс |
| Round trip Москва — Европа | ~30–50 мс |
| Round trip между континентами | **~150 мс** |

**Три вывода, которые меняют проектирование:**

1. **NVMe схлопнул разрыв между памятью и диском на три порядка.** Раскладка «диск медленный, поэтому всё в память» устарела: случайное чтение с NVMe быстрее, чем round trip внутри ЦОД. Прежде чем строить кэш, проверь, не хватает ли просто быстрого диска.
2. **Round trip по 100-гигабитной фабрике ЦОД быстрее, чем прочитать мегабайт с вращающегося диска.** Сеть внутри ЦОД перестала быть узким местом по сравнению с диском.
3. **Межконтинентальный round trip — 150 мс, и это физика.** Ни один кэш и ни одна оптимизация это не обойдут. Если требование по задержке ниже — нужна точка присутствия рядом с пользователем, других вариантов нет.

## Бюджет задержки

Задержка складывается по цепочке. Если требование «p95 ≤ 300 мс», распиши бюджет по звеньям и убедись, что сумма сходится с запасом:

```
Пользователь → CDN/edge         20 мс
  → балансировщик                5 мс
  → API-шлюз (авторизация)      10 мс
  → сервис заказов              15 мс собственной логики
    → кэш (попадание)            2 мс
    → БД (промах кэша)          20 мс
  → сериализация ответа          5 мс
Итого при попадании в кэш:      57 мс
Итого при промахе:              77 мс
Запас до бюджета:              ~220 мс на хвосты и сеть
```

**Помни про удлинение хвоста:** если у каждого из N звеньев p99 = 200 мс, то p99 всей цепочки существенно хуже 200 мс. Чем больше звеньев, тем выше вероятность поймать хвост хотя бы в одном.

## Пропускная способность

| Ресурс | Порядок |
|---|---|
| HDD последовательное чтение | 150–250 МБ/с |
| HDD случайные операции | 100–200 IOPS |
| SATA SSD | 500 МБ/с, десятки тысяч IOPS |
| NVMe | 3–7 ГБ/с, сотни тысяч — миллионы IOPS |
| Сеть 1 Гбит/с | ~125 МБ/с |
| Сеть 10 Гбит/с | ~1,25 ГБ/с |
| Сеть 100 Гбит/с | ~12,5 ГБ/с |
| PostgreSQL, простые запросы, одна нода | единицы–десятки тысяч запросов/с |
| PostgreSQL, транзакции с записью, одна нода | тысячи TPS, дальше упор в fsync и блокировки |
| Redis, одна нода | сотни тысяч операций/с |
| Kafka, один брокер | сотни МБ/с, сотни тысяч сообщений/с |
| Nginx как обратный прокси, одна нода | десятки тысяч rps |
| Один экземпляр прикладного сервиса | сотни–тысячи rps, сильно зависит от логики |

**Важно про диски:** для базы данных значение имеет не последовательная полоса, а **IOPS случайного доступа и задержка fsync**. Утверждение «HDD даёт 200 МБ/с, значит потянет» — ошибка: та же дисковая подсистема даст 150 IOPS случайной записи и станет узким местом на тысяче TPS.

## Методика оценки

### Шаг 1. RPS из аудитории

```
DAU × действий на пользователя в сутки ÷ 86 400 = средний RPS
средний RPS × коэффициент пика            = пиковый RPS
```

Коэффициент пика: для сервиса с суточным профилем обычно 2–5; для событийной нагрузки (распродажа, трансляция, рассылка) — 10–100.

**Проектируем под пиковый RPS. Средний нужен только для оценки стоимости.**

### Шаг 2. Объём данных

```
записей в сутки × размер записи × 365 = прирост за год
```

Затем умножить на:
- **×1,3–2** на индексы (иногда индексы весят больше данных);
- **×число реплик** на копии;
- **×1,3** на служебный оверхед хранилища и фрагментацию;
- **+бэкапы** за срок их хранения.

Итог «5 ТБ полезных данных» на практике означает 15–20 ТБ занятого места.

### Шаг 3. Трафик

```
RPS × средний размер ответа = полоса
```

Медиа считать отдельно: обычно именно оно, а не API, определяет счёт за трафик и необходимость CDN.

### Шаг 4. Куда упрёмся первым

Пройди по четырём ресурсам и назови, какой закончится раньше:
- **CPU** — при вычислительной логике, сериализации, шифровании;
- **память** — при кэшах, больших рабочих наборах, соединениях;
- **диск** — IOPS при случайном доступе, объём при росте, полоса при аналитике;
- **сеть** — при медиа, при болтливых межсервисных вызовах, при репликации.

**Это и есть главный результат оценки.** Он определяет, что оптимизировать и что масштабировать.

### Шаг 5. Headroom

Не планируй загрузку выше **60–70% CPU** для сервисов, чувствительных к задержке. Оставшееся — не простой, а плата за предсказуемые хвосты и запас на пик. Для батчей и аналитики допустимо 80–90%.

### Шаг 6. Порядок стоимости

Считать не в рублях за конкретный прайс, а в единицах инфраструктуры: сколько нод какого класса, сколько терабайт, сколько трафика. Затем перевести в деньги по прайсу целевой площадки.

Ожидаемый результат: **«инфраструктура порядка N сотен тысяч рублей в месяц при таких-то SLA»** — внятная проверка на реалистичность, а не точный прайс-лист.

## Единицы

- 10³ = тысяча, 10⁶ = миллион (мегабайт), 10⁹ = миллиард (гигабайт), 10¹² = триллион (терабайт)
- 86 400 секунд в сутках; удобно помнить, что **1 млн событий в сутки ≈ 11,6 в секунду**
- 2,6 млн секунд в месяце
- Различие МБ и МиБ при прикидке порядка игнорируется, при расчёте квот — нет

## Пример полного расчёта

**Задача:** лента соцсети. DAU 1 млн, каждый пользователь открывает ленту 10 раз в сутки, пишет пост раз в 50 дней, средний пост 500 КБ (с изображением).

```
Чтения:  1 000 000 × 10 / 86 400        = 116 rps в среднем
Пик ×5                                   = 580 rps
Записи:  1 000 000 / 50                  = 20 000 постов в сутки = 0,23 rps
Объём:   20 000 × 500 КБ                 = 10 ГБ в сутки
За год:  10 ГБ × 365                     = 3,65 ТБ
С индексами и 3 репликами                ≈ 15 ТБ
Трафик чтения: 580 rps × 500 КБ          = 290 МБ/с = 2,3 Гбит/с
```

**Что из этого следует:**
- 580 rps на чтение — это единицы прикладных нод, не десятки. Шардирование не нужно;
- 2,3 Гбит/с медиатрафика — **упрёмся в сеть и в стоимость трафика раньше, чем в базу**. Нужен CDN, и это главное архитектурное следствие расчёта;
- 15 ТБ за год — одна нода по объёму тянет, но бэкап и восстановление такого объёма надо проверять по RTO;
- соотношение чтений к записям 500:1 — классический случай для реплик чтения и агрессивного кэширования.

**Обрати внимание:** расчёт изменил архитектуру. Без него естественным решением было бы масштабировать базу; на самом деле узкое место — раздача медиа.
