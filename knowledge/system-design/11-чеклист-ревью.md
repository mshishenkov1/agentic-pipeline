# Чек-лист архитектурного ревью

Для `review-agent` и для самопроверки архитектора. Структура по шести столпам Well-Architected плюс каталог типовых дефектов.

**Правило заполнения: на каждый вопрос ответ «да, потому что…» со ссылкой на раздел документа, «нет, и вот почему это приемлемо» или «неприменимо, потому что…». Пустой ответ и «да» без обоснования считаются отрицательными.**

---

## Столп 1. Надёжность

- [ ] По каждому компоненту известно, что происходит при его отказе, и это записано в матрице деградации
- [ ] Ни один отказ не имеет радиуса поражения «все пользователи»
- [ ] Нет единых точек отказа, кроме явно принятых и записанных в риски
- [ ] На каждом сетевом вызове задан таймаут
- [ ] Ретраит ровно один слой цепочки, слой назван явно; есть потолок попыток и джиттер
- [ ] Circuit breaker на синхронных вызовах внешних систем
- [ ] Заданы RPO и RTO, и выбранная топология им соответствует
- [ ] Процедура восстановления описана и проверяема
- [ ] Деплой не требует простоя; откат возможен
- [ ] Схема эволюционирует по expand/contract; версия N кода работает со схемой N−1
- [ ] Мутирующие операции идемпотентны
- [ ] Есть механизм, гарантирующий, что событие публикуется тогда и только тогда, когда изменилось состояние (outbox или эквивалент)

## Столп 2. Безопасность

- [ ] Классы данных определены; известно, где лежат персональные и платёжные
- [ ] Шифрование при передаче и хранении для чувствительных данных
- [ ] Аутентификация и авторизация описаны; модель доступа явная
- [ ] Секреты не в коде и не в переменных окружения открытым текстом
- [ ] Межсервисное взаимодействие аутентифицировано
- [ ] Поверхность атаки минимальна: наружу торчит только то, что должно
- [ ] Ввод валидируется на границе; лимиты запросов на публичных точках
- [ ] Аудит действий: что пишется, где хранится, кто имеет доступ
- [ ] Требования резидентности выполняются **включая бэкапы, логи и трассировки**
- [ ] Есть процедура удаления данных субъекта сквозь все хранилища

## Столп 3. Производительность

- [ ] Требования по задержке заданы в перцентилях, а не в среднем
- [ ] Бюджет задержки расписан по звеньям и сходится с требованием
- [ ] Посчитано узкое место: CPU, память, диск или сеть
- [ ] Заявленный RPS проходит через выбранные хранилища — проверено расчётом
- [ ] Кэш применён там, где оправдан, и не применён там, где вреден
- [ ] Стратегия инвалидации соответствует критичности данных
- [ ] Учтено удлинение хвоста в цепочках; есть средства борьбы
- [ ] Headroom по CPU оставлен для сервисов, чувствительных к задержке
- [ ] Нет синхронных цепочек длиннее необходимого

## Столп 4. Операционное совершенство

- [ ] У каждого компонента есть метрики, логи и трассировка
- [ ] Сквозной идентификатор запроса проходит через все компоненты
- [ ] SLI и SLO определены на пользовательские сценарии, а не на технические метрики
- [ ] Алерты на симптомы, а не на причины; для каждого понятно действие
- [ ] Есть runbook на каждый предвиденный тип инцидента
- [ ] Стратегия выката описана: канарейка, флаги, откат
- [ ] Понятно, кто эксплуатирует и хватает ли ему компетенции
- [ ] Конфигурация отделена от кода; изменение не требует пересборки

## Столп 5. Стоимость

- [ ] Посчитан порядок стоимости инфраструктуры
- [ ] Названа самая дорогая статья и проверено, что она оправдана требованием
- [ ] Учтена стоимость трафика, особенно исходящего и межрегионального
- [ ] Учтён объём с репликами, индексами и бэкапами, а не только полезные данные
- [ ] Учтена стоимость эксплуатации в человеко-часах
- [ ] Есть политика жизненного цикла данных: холодные данные не лежат на горячем хранилище
- [ ] Нет ресурсов, зарезервированных «на всякий случай» без расчёта

## Столп 6. Устойчивое развитие (эффективность ресурсов)

- [ ] Ресурсы соответствуют реальной нагрузке; нет систематического переобеспечения
- [ ] Есть механизм снижения потребления в периоды низкой нагрузки
- [ ] Данные не хранятся дольше, чем требуется

---

## Проверки, специфичные для нашего конвейера

- [ ] Каждое `REQ`/`NFR` покрыто компонентом либо явно вынесено в «Отложено» с причиной
- [ ] **Ни одного компонента без требования** — по каждому проверено: что перестанет выполняться, если его убрать
- [ ] Ключ шардирования выбран и обоснован, даже если шард один
- [ ] По каждому существенному решению есть ADR с разобранной альтернативой
- [ ] В каждом ADR заполнен раздел «при каких условиях выбор был бы другим»
- [ ] Слабые места спецификации выписаны в формате `W-NN`; критичные вынесены человеку
- [ ] Комплект диаграмм полон и синтаксически валиден
- [ ] Все стрелки на диаграммах подписаны «зачем» и «как»
- [ ] Идентификаторы `C-NN` в карте компонентов и на диаграммах совпадают
- [ ] Ответы на вопросы платформы (шаг 0) зафиксированы в разделе «Ограничения»

## Каталог типовых дефектов

Проверять целенаправленно — эти дефекты встречаются чаще всего.

### Избыточная сложность
- микросервисы без требования к независимому масштабированию или независимым релизам;
- шардирование до исчерпания индексов, кэша и реплик;
- брокер там, где хватает синхронного вызова с ретраем;
- мультирегион при допустимом простое в часы;
- service mesh при числе сервисов меньше десяти;
- CQRS и event sourcing без требования к аудиту истории;
- слой абстракции над единственной реализацией;
- собственная реализация того, что есть в стандартной библиотеке или в уже используемом продукте.

### Недостаточная проработка
- «масштабируется горизонтально» без указания, до какого предела и что дальше;
- нет ответа, что происходит при недоступности каждой внешней зависимости;
- нет расчёта — компоненты выбраны по ощущению;
- ключ шардирования не назван;
- согласованность не обсуждена: непонятно, где строгая, где итоговая;
- нет плана миграции схемы;
- наблюдаемость упомянута общими словами без перечня метрик.

### Ошибки распределённых систем
- синхронная цепочка из четырёх и более звеньев на пользовательском пути;
- ретраи на нескольких слоях одновременно;
- запись в БД и отправка события двумя отдельными действиями без outbox;
- расчёт на exactly-once через границу внешней системы;
- расчёт на порядок сообщений без единого ключа партиционирования;
- 2PC между микросервисами;
- общая БД у нескольких сервисов;
- чтение с реплики сразу после записи без учёта лага;
- распределённая блокировка как основной механизм согласования.

### Ошибки данных
- кэширование ошибок 5xx и таймаутов;
- TTL-инвалидация на критичных данных (адреса, балансы, права);
- аналитические запросы на боевой OLTP-базе;
- отсутствие партиционирования у растущей журнальной таблицы;
- денежные суммы в типе с плавающей точкой;
- время без часового пояса;
- отсутствие уникального ограничения там, где инвариант обязателен.

### Ошибки эксплуатации
- отсутствие таймаута хотя бы на одном сетевом вызове;
- деплой, требующий простоя;
- миграция, после которой невозможен откат;
- health-check, проверяющий только «процесс жив», а не «готов обслуживать»;
- data plane, зависящий от доступности control plane;
- непроверенное восстановление из бэкапа;
- секреты в репозитории или в логах;
- идентификаторы пользователей в метках метрик (взрыв кардинальности).

## Формат вердикта

```json
{
  "verdict": "approve | request_changes",
  "pillars": {
    "reliability":  {"passed": true,  "notes": "..."},
    "security":     {"passed": false, "notes": "..."},
    "performance":  {"passed": true,  "notes": "..."},
    "operations":   {"passed": true,  "notes": "..."},
    "cost":         {"passed": true,  "notes": "..."},
    "sustainability": {"passed": true, "notes": "..."}
  },
  "findings": [
    {
      "id": "F-01",
      "severity": "blocker | major | minor",
      "category": "избыточная сложность | недостаточная проработка | распределённые системы | данные | эксплуатация",
      "where": "system-design.md §5, C-04",
      "what": "конкретное замечание",
      "why_it_matters": "какое требование или свойство под угрозой",
      "must_fix": true,
      "assignee": "architect | intake | human"
    }
  ],
  "unjustified_complexity": ["C-07 — не обоснован ни одним требованием"],
  "missing_coverage": ["NFR-06 не покрыт и не вынесен в «Отложено»"]
}
```

`approve` — только если нет ни одного `must_fix` и все шесть столпов пройдены или явно помечены неприменимыми.
