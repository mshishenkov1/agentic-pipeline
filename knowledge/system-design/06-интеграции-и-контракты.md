# Интеграции, контракты, эволюция схемы

## Синхронно или асинхронно

**Умолчание — асинхронно.** Синхронный вызов оправдан только когда вызывающему нужен ответ, чтобы продолжить прямо сейчас: проверить баланс перед переводом, получить профиль перед отрисовкой формы.

**Цена синхронности — временная связанность: если исполнитель лежит, лежит и вызывающий.** Каждый синхронный вызов в цепочке перемножает недоступности: три звена по 99,9% дают 99,7%.

Асинхронно — когда: операция длительная; нужно пережить недоступность получателя; одно событие запускает несколько независимых процессов; нужно сгладить пик.

## Протоколы

| Протокол | Сильная сторона | Когда выбирать | Ограничения |
|---|---|---|---|
| **REST/HTTP** | универсальность, кэшируемость, отладка | публичные API, интеграции с разнородными системами | многословен, нет схемы по умолчанию |
| **gRPC** | производительность, строгая схема, стриминг | частые внутренние вызовы между сервисами | плохо через браузер без прокси, сложнее отлаживать |
| **GraphQL** | клиент запрашивает ровно нужное | много разных клиентов с разными потребностями | сложность кэширования, риск тяжёлых запросов, N+1 |
| **WebSocket** | двунаправленный поток | чаты, котировки, совместное редактирование | состояние соединения, сложность масштабирования |
| **SSE** | однонаправленный поток поверх HTTP | лента обновлений, прогресс | только сервер→клиент |
| **Long polling** | работает везде | фолбэк для legacy-клиентов | держит соединения, задержка |
| **Брокер сообщений** | развязка, буферизация, веерная рассылка | асинхронные процессы | сложность гарантий и порядка |

## Очередь или лог

Принципиальная развилка, которую путают.

**Очередь (RabbitMQ и подобные):** сообщение доставляется одному потребителю и исчезает. Модель «задача». Гибкая маршрутизация, приоритеты, TTL, dead letter queue. Подходит для распределения работы.

**Распределённый лог (Kafka и подобные):** сообщения хранятся заданное время, потребители читают со своей позиции, могут перечитать. Модель «поток событий». Порядок гарантирован в пределах партиции, масштабирование через партиции, несколько независимых групп потребителей одних и тех же данных. Подходит для событийной архитектуры, CDC, аналитики.

**Правило:** нужно раздать задачи исполнителям — очередь. Нужен поток событий, который читают несколько подсистем и можно перечитать — лог.

## Гарантии доставки

- **At-most-once** — может потеряться. Годится для телеметрии.
- **At-least-once** — не потеряется, но **возможны дубли**. Практический умолчательный режим.
- **Exactly-once** — существует только в узких рамках (транзакции внутри одной системы, например Kafka transactions producer→consumer→producer). **Через границу внешней системы exactly-once недостижим.**

**Единственный практичный подход: at-least-once доставка + идемпотентный потребитель.** Потребитель хранит идентификаторы обработанных сообщений либо делает операцию естественно идемпотентной (UPSERT по ключу, установка состояния вместо инкремента).

## Порядок сообщений

Порядок гарантируется только в пределах партиции. Следствия:
- сообщения по одной сущности должны идти **с одним ключом партиционирования**, иначе порядок не гарантирован;
- ключ партиционирования по сущности означает, что горячая сущность нагружает одну партицию;
- увеличение числа партиций меняет распределение ключей — планируй заранее.

Если порядок принципиально важен, а поток велик, проектируй так, чтобы **обработка была коммутативной** (результат не зависит от порядка) — это надёжнее, чем полагаться на глобальный порядок.

## Outbox — связь состояния и события

Классическая ошибка: записали в БД и отправили событие в брокер двумя отдельными действиями. При падении между ними состояние и события расходятся.

**Решение — transactional outbox:** изменение состояния и запись события в таблицу `outbox` происходят **в одной локальной транзакции**; отдельный процесс (или CDC-коннектор вроде Debezium) читает outbox и публикует в брокер, помечая отправленное. Гарантия: событие опубликовано тогда и только тогда, когда состояние изменилось. Дубли возможны — потребитель обязан быть идемпотентным.

**Обратный паттерн — inbox:** потребитель записывает идентификатор обработанного сообщения в таблицу в той же транзакции, что и эффект. Дубль отсекается по уникальному индексу.

## Контракты

### Что описывается

**REST:** путь и метод, path- и query-параметры, заголовки, тело запроса и ответа, схема каждого поля (тип, формат, обязательность, пример), правила валидации, **все коды ответов включая ошибки**. Формат — OpenAPI.

**События:** топик, схема сообщения, ключ партиционирования, гарантии, политика повторов и dead letter. Формат — AsyncAPI, схема — JSON Schema, Avro или Protobuf.

**Обязательно для обоих:** версия, владелец, кто уведомляется об изменении.

### Единый формат ошибок

Один формат на всю систему, иначе каждый клиент пишет свой разбор:

```json
{
  "code": "insufficient_funds",
  "message": "Недостаточно средств на счёте",
  "details": [{"field": "amount", "issue": "exceeds_balance"}],
  "trace_id": "01J8ZQ..."
}
```

Машиночитаемый `code` стабилен и является частью контракта; `message` для человека и может меняться. `trace_id` обязателен — по нему клиент и поддержка находят запрос в трассировках.

### Идемпотентность

Каждая мутирующая операция принимает **ключ идемпотентности** (заголовок `Idempotency-Key`). Сервер хранит результат первой обработки и при повторе с тем же ключом возвращает **тот же ответ, не выполняя операцию повторно**. Срок хранения ключа — часть контракта (обычно 24 часа).

Это не опция, а базовое требование: сеть ненадёжна, клиенты повторяют запросы, пользователи жмут кнопку дважды.

### Версионирование и совместимость

- **Обратно совместимые изменения** (добавление необязательного поля, нового кода ошибки, нового эндпоинта) — без смены версии.
- **Ломающие** (удаление или переименование поля, изменение типа, ужесточение валидации, изменение семантики) — новая версия.
- **Правило расширения (expand/contract) для API:** новое поле добавляется как необязательное → клиенты переходят → старое объявляется устаревшим → удаляется после подтверждения, что никто не использует.
- **Заголовок версии клиента** (`X-Client-Version`) позволяет вести поведение по версии приложения там, где версионировать путь нецелесообразно — особенно для мобильных, где пользователи годами сидят на старых сборках.
- Для схем событий — **реестр схем** с проверкой совместимости при публикации.

### Пагинация

- **Offset** — просто, позволяет прыгать на страницу; **замедляется с ростом смещения и даёт дубли/пропуски при изменении данных**.
- **Курсорная** — стабильна на меняющихся данных, не замедляется; нельзя прыгнуть на произвольную страницу. **Умолчание для лент и любых часто меняющихся списков.**
- Курсор должен быть непрозрачным для клиента (base64 от внутреннего состояния) — иначе он становится частью контракта.

## Эволюция схемы данных без простоя

**Expand/contract — обязательный порядок для любого изменения схемы:**

1. **Expand.** Добавить новое (колонку, таблицу, индекс) так, чтобы старый код продолжал работать. Новая колонка nullable или с умолчанием.
2. **Двойная запись.** Код пишет и в старое, и в новое.
3. **Backfill.** Перенести исторические данные фоново, порциями, с контролем нагрузки.
4. **Переключение чтения** на новое, с возможностью откатиться.
5. **Contract.** Убрать двойную запись, затем удалить старое — **отдельным релизом, после подтверждения, что откат не понадобится**.

**Чего нельзя делать в одном шаге:** переименовать колонку, изменить тип с сужением, добавить NOT NULL без умолчания на большой таблице, создать индекс в блокирующем режиме, удалить то, что ещё читается предыдущей версией кода.

**Правило совместимости релизов:** версия N кода обязана работать со схемой версий N−1 и N. Иначе откат релиза невозможен.

Для больших таблиц — инструменты онлайн-изменений (`pg_repack`, `gh-ost`, `pt-online-schema-change`) вместо блокирующего ALTER.

## Внешние зависимости

По каждой внешней системе зафиксировать:
- её SLA и что делаем, когда она его не выполняет;
- лимиты запросов и как их соблюдаем;
- таймаут и circuit breaker;
- **поведение при недоступности: отказ, деградация или отложенная обработка** — это архитектурное решение, а не деталь реализации;
- как тестируем без неё (мок, песочница, контрактные тесты).

**Anti-corruption layer:** внешняя модель не проникает внутрь домена. Адаптер переводит внешние структуры во внутренние. Без него смена поставщика превращается в переписывание системы.
