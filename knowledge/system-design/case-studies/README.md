# Разборы реальных архитектур

Единый формат: **задача → числа → ключевые решения → что переделывали и почему → чему учит**.

Раздел «что переделывали» важнее раздела «как устроено». Он единственный лечит соблазн строить конечную архитектуру сразу.

Помечено: ✅ — проверено по первоисточнику (инженерный блог компании, официальная документация) в августе 2026; ⚠️ — по памяти, требует проверки перед использованием как аргумента.

---

## 1. Discord — хранение триллионов сообщений ✅

**Задача.** Хранить и быстро читать историю сообщений; нагрузка крайне неравномерна — есть каналы-гиганты и мёртвые каналы.

**Числа.** Триллионы сообщений. Кластер сокращён со **177 нод Cassandra до 72 нод ScyllaDB**; на ноду ~9 ТБ против ~4 ТБ ранее. Задержка чтения истории: p99 упал с **40–125 мс до 15 мс**; вставка — с 5–70 мс до стабильных **5 мс**. Мигратор на Rust перекладывал до **3,2 млн сообщений в секунду**.

**Ключевые решения.**
- Партиционирование сообщений по каналу и временному интервалу (bucket) — иначе активный канал даёт неограниченно растущую партицию.
- **Слой data services на Rust между API и базой** — тонкий, по одному gRPC-эндпоинту на запрос, почти без бизнес-логики.
- **Request coalescing:** одновременные запросы одних и тех же данных схлопываются в один запрос к базе.
- **Consistent hashing по идентификатору канала** для маршрутизации на инстансы data service — так запросы одного канала попадают на один инстанс, и склейка работает эффективно.

**Что переделывали.** MongoDB → Cassandra → ScyllaDB. Cassandra перестала устраивать из-за: **горячих партиций** (популярный канал ронял задержку всего кластера, потому что чтения дороже записей), **пауз сборщика мусора JVM**, **неуправляемого отставания компакции** — команде приходилось регулярно выполнять ручные процедуры обслуживания.

**Чему учит.**
1. Горячий ключ ломает даже правильно спроектированное шардирование — нужен отдельный механизм.
2. Request coalescing — дешёвый способ срезать пик, работающий только в связке с маршрутизацией по тому же ключу.
3. Смена реализации при той же модели данных (Cassandra → ScyllaDB, совместимы по протоколу) — иногда самый дешёвый способ решить проблему производительности: сократили парк в 2,5 раза и сняли класс проблем с GC.

## 2. Figma — масштабирование Postgres ✅

**Задача.** Одна RDS-инстанция Postgres с метаданными (права, файлы, комментарии) при росте трафика примерно **втрое в год**.

**Числа.** К 2020 году **утилизация CPU достигала 65%** в пик. «Если база полностью насытится, Figma перестанет работать». В крупнейшей операции переносили **50 таблиц за раз**; влияние на доступность — около **30 секунд частичной деградации, ~2% потерянных запросов**. Утилизация крупнейшего раздела после разделения упала до **~10%**.

**Ключевые решения — строго по лестнице.**
1. Вертикальное масштабирование: r5.12xlarge → r5.24xlarge.
2. Реплики чтения.
3. Новые сценарии — в отдельные базы, чтобы не растить исходную.
4. PgBouncer как пул соединений.
5. И только потом — **вертикальное партиционирование**: группы связанных таблиц переезжают в отдельные базы.

**Почему не горизонтальный шардинг сразу.** Управляемые Postgres-совместимые решения не подходили по масштабу; переход на NoSQL или Vitess требовал сложной двойной записи и чтения; самостоятельный хостинг распределённого Postgres означал большие операционные издержки без доказанной выгоды.

**Как выбирали, что выносить.** Два критерия: **влияние** (высокая утилизация CPU, измеренная через average active sessions) и **изолированность** (минимум внешних ключей к остальным таблицам). Написали валидаторы в ActiveRecord, чтобы отследить, какие физические таблицы задействует каждый запрос, и выгружали статистику в Snowflake.

**Как переносили.** Логическая репликация вместо потоковой — позволяет реплицировать подмножество таблиц и откатываться обратной репликацией. **Индексы удаляли на время начального копирования и строили после — миграция сократилась с недель до часов.** Переключение: догнать лаг до нуля → приостановить запись → сверить позиции журнала (LSN) → повысить реплику → включить обратную репликацию → пустить трафик.

**Чему учит.**
1. Лестница вмешательств работает: четыре ступени дали годы запаса.
2. Вертикальное партиционирование — недооценённая ступень между «реплики» и «шардинг», часто достаточная.
3. Обратная репликация как страховка отката — обязательный элемент миграции.
4. Решение измеряли, а не угадывали: валидаторы запросов дали фактическую картину нагрузки по таблицам.

## 3. Slack — переход к ячеистой архитектуре ✅

**Задача.** Сервисы распределены по зонам доступности, но продолжают отказывать целиком при проблеме в одной зоне.

**Инцидент-триггер.** **30 июня 2021** отказ сетевого канала в одной зоне доступности региона us-east-1 вызвал видимый пользователям сбой. Автоматически смягчить не смогли: **разные компоненты по-разному видели доступность системы** — «серый» отказ. Обнаружение и устранение оказались слишком сложны для автоматики.

**Решение.** **Ячейка = зона доступности.** Сервисы развёрнуты во всех зонах, но **общаются только внутри своей зоны**. Фактически N независимых виртуальных экземпляров системы.

**Слив трафика.** Вместо доработки каждого сервиса на разных языках слив реализован **на пограничном слое**: сигнал через внутреннюю систему заставляет пограничные балансировщики Envoy перевзвесить кластеры по зонам. Используются weighted clusters и динамические веса — **гранулярность 1%**.

**Что решили ячейки, чего не решала мультизональность.** Раньше отказ одной зоны каскадом расходился по остальным, потому что сервисы ходили к бэкендам во все зоны. Теперь отказ внутри зоны **локализован в этой зоне**, и оператору достаточно увести трафик, не разбираясь в природе сбоя.

**Чему учит.**
1. Размещение в нескольких зонах само по себе не даёт изоляции. Изоляция появляется, только когда **запрещены перекрёстные вызовы**.
2. «Серые» отказы опаснее явных: автоматика не срабатывает, потому что компоненты расходятся в оценке живости.
3. Механизм реагирования дешевле строить в одном месте (периметр), чем в каждом сервисе.
4. Возможность увести трафик, не поставив диагноз, — самостоятельная ценность.

## 4. Uber — H3, гексагональный пространственный индекс ✅

**Задача.** Анализировать миллионы событий маркетплейса по городам: спрос, предложение, динамическое ценообразование. Почтовые индексы и произвольные операционные зоны непригодны — разной формы и часто меняются; анализ по точным координатам вычислительно дорог.

**Решение.** Иерархическая гексагональная сетка, **16 уровней разрешения**, каждый следующий примерно в 7 раз мельче.

**Почему гексагоны.** У шестиугольника **одно расстояние до всех соседей**; у квадрата их два (сторона и диагональ), у треугольника — три. Это радикально упрощает анализ и сглаживание градиентов. Идентификатор потомка **усекается до предка**, что даёт эффективную иерархическую индексацию.

**Применение.** Расчёт спроса и предложения внутри гексагонов для сурж-ценообразования, диспетчеризация и объединение поездок, анализ трендов с переменной детализацией, аппроксимация радиуса поиска соседними гексагонами. Открытый исходный код, привязки для Java, JavaScript, Python, Go.

**Чему учит.**
1. Выбор системы координат — архитектурное решение с далеко идущими последствиями, а не деталь реализации.
2. Свойство «равное расстояние до соседей» показывает, как геометрия структуры данных прямо влияет на сложность прикладной логики.
3. Иерархия с усечением идентификатора даёт агрегацию на разных уровнях без пересчёта.

## 5. Amazon / AWS — cell-based architecture и shuffle sharding ✅

**Задача.** Ограничить радиус поражения отказа в мультиарендных сервисах глобального масштаба.

**Решение.** Ячейка — полный самодостаточный экземпляр сервиса, обслуживающий подмножество клиентов и не обращающийся к другим ячейкам. Тонкий маршрутизатор направляет запрос по ключу. Подход применяется в сервисах AWS более десяти лет и оформлен как развитие практики bulkhead из столпа надёжности Well-Architected.

**Shuffle sharding.** Клиенту назначается не одна ячейка, а **случайная комбинация узлов**. Число комбинаций растёт комбинаторно, поэтому вероятность совпадения наборов у двух клиентов мала. Отравленный запрос или злоупотребление одного клиента задевает лишь тех, кто делит с ним **весь** набор, — доли процента вместо всех.

**Сопутствующие принципы.** Разделение control plane и data plane; **static stability** — data plane продолжает работать на последней известной конфигурации при отказе control plane.

**Чему учит.**
1. Радиус поражения — проектируемая величина, а не следствие.
2. Маршрутизатор обязан быть тривиальным: он единственный общий компонент, и его отказ отменяет всю схему.
3. Не делать работающий контур зависимым от управляющего.

## 6. Vitess — горизонтальное шардирование MySQL ✅

**Что это.** Слой между приложением и MySQL, делающий шардированную базу похожей на монолитную: прозрачное шардирование, мультиплексирование соединений, онлайн-изменение схемы. Приложение не знает о распределении данных.

**Числа.** JD.com на пике «дня холостяка» проводил через Vitess **35 млн запросов в секунду**. В YouTube используется с 2011 года, выросло до десятков тысяч нод MySQL. Применяется также в Slack и Square.

**Чему учит.**
1. Шардирование можно скрыть от приложения — но ценой отдельного координатора, который нужно эксплуатировать.
2. Онлайн-изменение схемы — отдельная сложная задача, ради которой стоит брать готовый инструмент.

⚠️ **Про часто цитируемое «GitHub держал 950 тысяч транзакций в секунду на монолитной базе».** Проверить это утверждение не удалось; известно обратное — GitHub публично описывал **разделение своих реляционных баз** для работы с масштабом. Тезис «не шардируйте раньше времени» верен, но подкреплять его этим числом не следует.

## 7. Stripe — идемпотентность как свойство продукта ⚠️

**Задача.** Платёжный API поверх ненадёжной сети: клиент не знает, дошёл ли запрос, и повторяет его.

**Решение.** Заголовок `Idempotency-Key` на всех мутирующих операциях. Сервер сохраняет результат первой обработки и при повторе с тем же ключом возвращает **тот же ответ**, не выполняя операцию заново. Срок жизни ключа — часть публичного контракта. Версионирование API закреплено за аккаунтом: клиент не ломается от изменений, пока сам не переключит версию.

**Чему учит.**
1. Идемпотентность — не деталь реализации, а часть контракта, которую видит и на которую опирается клиент.
2. Стабильность API можно сделать продуктовым преимуществом.

## 8. Netflix — устойчивость через управляемый отказ ⚠️

**Ключевые практики.** Chaos engineering: намеренные отказы в проде, чтобы устойчивость проверялась постоянно, а не в теории. Региональный failover как отработанная процедура. Fallback на каждом уровне: не удалось получить персональные рекомендации — отдаётся неперсонализированный список. Библиотеки стабильности (таймауты, bulkhead, circuit breaker) вынесены в общую инфраструктуру, чтобы каждая команда не изобретала их заново.

**Чему учит.**
1. Непроверенная отказоустойчивость не существует.
2. Деградация проектируется на каждом уровне, а не на одном.
3. Паттерны стабильности лучше давать командам как готовую инфраструктуру, чем как рекомендацию.

## 9. Shopify — pods ⚠️

**Задача.** Мультиарендность при экстремальных всплесках (флеш-распродажи, чёрная пятница).

**Решение.** Магазины распределены по **подам** — изолированным наборам приложения и базы. Под — фактически ячейка. Всплеск в одном магазине ограничен его подом. Крупные магазины могут выноситься в отдельные поды.

**Чему учит.**
1. Мультиарендность и ячейки естественно сочетаются: арендатор — готовый ключ разбиения.
2. Разделение арендаторов по размеру решает проблему горячего ключа.

## 10. Instagram — масштаб малой командой ⚠️

**Решение.** Долго держались на Django и PostgreSQL, шардируя вручную по идентификатору пользователя; собственная генерация идентификаторов, кодирующая шард прямо в ID, — так по любому ID сразу известно, где искать данные. Дисциплина простоты: мало технологий, глубокая экспертиза в каждой.

**Чему учит.**
1. Масштаб достигается дисциплиной и правильными ключами, а не количеством технологий.
2. Кодирование шарда в идентификаторе избавляет от справочника маршрутизации.

## Сводка: что общего у всех

1. **Никто не начинал с текущей архитектуры.** Все переписывались, и это было нормальной частью развития.
2. **Переход на следующую ступень происходил, когда предыдущая исчерпывалась, — с измерением, а не с предчувствием.**
3. **Горячие ключи и неравномерность нагрузки** — причина большинства переделок, а не общий объём.
4. **Изоляция (ячейки, поды, шардинг арендаторов)** — универсальный ответ на «как ограничить последствия отказа».
5. **Инструменты, снимающие целый класс проблем** (ScyllaDB вместо GC-пауз, Vitess вместо ручного шардирования, логическая репликация вместо простоя), окупаются лучше точечных оптимизаций.
