# Выбор языка и стека под задачу

**Язык выбирается под компонент, а не под проект.** Один сервис может быть на Go, другой на Python — если это обосновано профилем нагрузки. Но каждый дополнительный язык в системе стоит денег постоянно, поэтому разноязычие требует обоснования не меньшего, чем шардирование.

Архитектор **обязан предложить язык по каждому компоненту** и обосновать выбор. Компонент без указанного языка и обоснования — незавершённое проектирование.

---

## Порядок критериев

Веса именно такие. Пункт выше перебивает пункт ниже.

### 1. Экспертиза команды — перебивает всё

Язык, которым команда не владеет, добавляет к сроку не проценты, а разы, и весь этот срок код пишется плохо. Технически идеальный выбор при отсутствии людей — плохой выбор.

**Исключение только одно:** профиль нагрузки делает привычный стек физически непригодным (см. критерий 2), и это доказано числами. Тогда выбор языка становится решением о найме и обучении — и оформляется ADR с оценкой этой стоимости.

### 2. Пригодность под профиль нагрузки

Единственный критерий, способный перебить экспертизу. Проверяется числами из расчёта, а не общими словами о производительности.

| Профиль | Что определяет пригодность | Подходят | Плохо подходят |
|---|---|---|---|
| **IO-bound, много одновременных соединений** (API-шлюзы, прокси, чаты, стриминг событий) | стоимость одного соединения и переключения | Go (горутины), Rust, Erlang/Elixir, Node.js, Python с async | Python синхронный, Java на потоках без виртуальных |
| **CPU-bound** (шифрование, сжатие, обработка изображений, ML-инференс) | скорость вычислений, отсутствие пауз GC | Rust, C++, Go, Java с JIT | Python, Ruby, PHP — за исключением обёрток над нативными библиотеками |
| **Жёсткие требования к хвосту задержки** (p99 в единицах мс) | предсказуемость, отсутствие пауз сборщика мусора | Rust, C++, Go (короткие паузы) | JVM без тюнинга GC, любые языки со stop-the-world |
| **Обработка данных и аналитика** | зрелость экосистемы, а не скорость языка | Python (pandas, Spark), Scala, SQL | Go, Rust — экосистема беднее, выигрыш съедается разработкой |
| **ML и работа с моделями** | доступность библиотек | Python — де-факто безальтернативен | все остальные |
| **Бизнес-логика, CRUD, интеграции** | скорость разработки и поддерживаемости | почти любой; решает критерий 1 | — |
| **Долгоживущие фоновые процессы, надёжность при отказах** | модель супервизии | Erlang/Elixir, Go | — |
| **Скрипты, автоматизация, инструменты** | скорость написания | Python, Bash, Go для распространяемых бинарников | — |

### 3. Экосистема под конкретную задачу

Драйвер к нужной СУБД, зрелый клиент к брокеру, библиотека протокола. **Отсутствие зрелой библиотеки под ключевую интеграцию перевешивает языковые достоинства:** писать свой клиент к Kafka — это отдельный проект внутри проекта.

### 4. Найм и замена

Насколько легко найти разработчика в вашем регионе и как быстро он войдёт в проект. Экзотический язык означает, что уход одного человека останавливает сервис.

### 5. Эксплуатационная стоимость

Размер образа, потребление памяти, время старта (важно для автомасштабирования и serverless), инструменты профилирования в проде, зрелость сборки и поставки.

### 6. Совместимость с ландшафтом

Что уже принято в компании, есть ли внутренние библиотеки, шаблоны сервисов, поддержка в CI.

## Правило разноязычия

**Умолчание — один язык на систему.** Каждый дополнительный добавляет постоянные издержки: своя сборка, свои линтеры, свой мутационный инструмент, своя цепочка поставки, свои дежурства, свои эксперты, невозможность переиспользовать код между сервисами.

Второй язык оправдан, когда **выполнены оба условия**:
1. есть компонент с профилем нагрузки, для которого основной язык непригоден **по числам из расчёта**;
2. этот компонент имеет чёткую границу и общается по контракту, а не разделяет код с остальными.

Классический оправданный случай: система на Python, а шлюз, держащий 50 000 WebSocket-соединений, — на Go. Классический неоправданный: «этот сервис напишем на Rust, потому что он производительнее» без единого числа.

**Третий язык требует особого обоснования.** Практически всегда это признак того, что решения принимались по вкусу разработчиков, а не по требованиям.

---

## Что считается обоснованием, а что нет

**Обоснование:**
- «NFR-02 требует 12 000 одновременных соединений при p99 ≤ 50 мс; расчёт даёт ~200 МБ памяти на Go против ~4 ГБ на синхронном Python при том же числе соединений»;
- «команда из шести человек, пять пишут на Go, обучение шестого — две недели»;
- «нужен клиент к ClickHouse с поддержкой нативного протокола; зрелый есть только для Go и Python»;
- «сервис вызывается раз в сутки, требований к задержке нет — берём язык, на котором быстрее написать».

**Не обоснование:**
- «Go быстрее Python» — быстрее в чём и насколько, и упираемся ли мы в это;
- «Rust безопаснее» — какая конкретно проблема безопасности стоит переобучения команды;
- «это современный стек»;
- «на этом языке интереснее писать»;
- «так делают в больших компаниях» — у них другая команда, другой масштаб и свои платформенные библиотеки.

## Стоимость каждого языка в конвейере

Заводя язык, вы обязуетесь настроить и поддерживать полный набор. **Если для языка нет чего-то из списка, соответствующий гейт по этому сервису отключается — то есть качество там ниже.** Это надо назвать явно при выборе.

| Что нужно | Python | Go | TypeScript | Java | Rust |
|---|---|---|---|---|---|
| Тесты | pytest | `go test` | vitest, jest | JUnit | `cargo test` |
| Линтер | ruff | golangci-lint | eslint | checkstyle | clippy |
| Типизация | mypy | встроена | tsc | встроена | встроена |
| Покрытие | pytest-cov | `go test -cover` | c8, istanbul | JaCoCo | tarpaulin |
| **Мутационное тестирование** | mutmut | gremlins | Stryker | PIT | cargo-mutants |
| Контрактные тесты | schemathesis, pact | pact-go | pact-js | pact-jvm | — |
| Тесты с инфраструктурой | testcontainers | testcontainers-go | testcontainers-node | testcontainers-java | testcontainers-rs |

**Мутационное тестирование — главный риск при выборе языка**, потому что именно оно ловит тавтологичные тесты, а инструменты для него зрелые не везде. Язык без работающего мутационного инструмента означает, что G3 по этому сервису не работает и качество тестов там проверяется только на ревью.

## Формат предложения архитектора

По каждому компоненту в карте:

```markdown
### C-03: Шлюз реального времени
- **зона ответственности:** держит WebSocket-соединения клиентов и раздаёт обновления
- **модуль:** services/realtime
- **язык:** Go
- **обоснование языка:** NFR-04 требует 12 000 одновременных соединений при
  p99 ≤ 50 мс. Основной язык системы (Python) при таком числе соединений
  потребует ~4 ГБ памяти на инстанс против ~200 МБ на Go, а хвост задержки
  зависит от GIL. Команда: двое из шести владеют Go. Мутационное
  тестирование — gremlins, настроено. Альтернатива — Python с asyncio —
  рассмотрена в ADR-006 и отвергнута по памяти на соединение.
- **требования:** NFR-04, REQ-07
```

**Выбор языка, отличного от основного языка системы, обязательно требует ADR** (см. `08-критерии-решений-и-adr.md`) с разобранной альтернативой «сделать на основном языке» и честной оценкой, чем платим.

## Типовые ошибки

- **Выбор по бенчмаркам вместо профиля.** Синтетический бенчмарк меряет не вашу нагрузку. Значение имеет только то, во что упирается ваша система.
- **Оптимизация языка вместо архитектуры.** Смена языка даёт единицы раз; правильный кэш или индекс — порядки. Прежде чем переписывать на быстрый язык, пройди лестницу вмешательств.
- **Разноязычие ради интереса разработчиков.** Обходится компании дороже всего и вскрывается через год, когда автор уходит.
- **Игнорирование времени старта.** Для автомасштабирования и serverless холодный старт JVM может перечеркнуть выигрыш в пропускной способности.
- **Единый язык вопреки очевидной непригодности.** Обратная крайность: писать ML на Go, потому что «у нас всё на Go».
