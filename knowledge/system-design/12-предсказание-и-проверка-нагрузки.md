# Предсказание, симуляция и проверка нагрузки

Замкнутый цикл, превращающий оценку из угадывания в проверяемое утверждение:

```
предсказание → симуляция → постройка → измерение → калибровка → следующее предсказание
   (архитектор)  (simulate.py)  (dev)     (perf-agent)  (check_capacity)
```

**Правило: архитектор обязан зафиксировать числовое предсказание ДО постройки.** Предсказание, сформулированное после измерения, ничего не стоит и ничему не учит.

---

## 1. Формат предсказаний

Раздел `## Предсказания нагрузки` в `system-design.md`, машиночитаемый блок YAML. Проверяется гейтом G10.

```yaml
predictions:
  - id: P-01
    scenario: create_order            # имя сценария, совпадает с именем нагрузочного теста
    entrypoint: "POST /orders"        # что дёргаем
    requirements: [NFR-01, NFR-02]    # какие требования проверяет
    target_rps: 580                   # пиковая нагрузка из расчёта
    p95_ms: 300                       # предсказанная задержка
    p99_ms: 800
    saturation_rps: 1200              # где ожидаем насыщение системы
    bottleneck: "C-04 PostgreSQL — запись, fsync"
    error_budget_pct: 0.1             # допустимая доля ошибок под нагрузкой
    confidence: medium                # low | medium | high
    basis: "расчёт §Оценка нагрузки; 4 записи на заказ, IOPS диска 12k"
```

**Поля `saturation_rps` и `bottleneck` обязательны.** Именно они отличают инженерное предсказание от пожелания: «масштабируется» без указания предела — незаконный ответ (см. `08-критерии-решений-и-adr.md`).

`confidence` влияет на допустимое расхождение в гейте:

| Уверенность | Когда ставить | Допустимое расхождение |
|---|---|---|
| `high` | есть измерения аналогичной системы или калибровка по прошлым прогонам | ×1,5 |
| `medium` | расчёт по справочным числам, компоненты знакомы | ×2 |
| `low` | новая технология, непроверенный паттерн нагрузки | ×3 |

Завышенная уверенность наказывается: если поставил `high` и промахнулся вдвое — гейт красный.

## 2. Симуляция до постройки

`scripts/simulate.py` строит модель массового обслуживания по карте компонентов и профилю нагрузки и отвечает на вопрос **«где насытится и при каком RPS»** — до того, как что-то построено.

### Что моделируется

Каждый компонент — узел обслуживания с параметрами: время обслуживания одного запроса, число параллельных обработчиков, доля запросов сценария, проходящая через него. Модель считает по цепочке:

- **загрузка узла** ρ = λ / (c · μ), где λ — входящий поток, c — число обработчиков, μ — скорость одного;
- **ожидание в очереди** по формуле Эрланга C (M/M/c);
- **задержка сценария** — сумма по цепочке, включая ожидание;
- **точка насыщения** — минимальный RPS, при котором любой узел достигает ρ ≥ 1;
- **хвост** — приближённая оценка p95/p99 с учётом числа звеньев.

### Что модель даёт и чего не даёт

**Даёт:** порядок точки насыщения, какой узел упрётся первым, чувствительность к числу реплик, эффект добавления звена в цепочку.

**Не даёт:** реальных хвостов (модель не знает про сборку мусора, троттлинг, noisy neighbor), поведения при перегрузке (реальная система деградирует нелинейно), эффектов кэша.

**Модель — это фильтр здравого смысла, а не предсказание.** Она ловит «этот дизайн упрётся в 300 rps, а требование 5000» до постройки. Расхождение модели с измерением в два раза — норма; расхождение на порядок означает ошибку в модели или в дизайне.

### Формат входа

Раздел `## Модель нагрузки` в `system-design.md`:

```yaml
model:
  scenarios:
    - id: create_order
      rps: 580
      chain:                          # последовательность узлов
        - {component: C-01, service_ms: 8,  concurrency: 24}
        - {component: C-04, service_ms: 12, concurrency: 32, share: 1.0}
        - {component: C-06, service_ms: 2,  concurrency: 8,  share: 1.0, async: true}
    - id: list_catalog
      rps: 4200
      chain:
        - {component: C-02, service_ms: 4,  concurrency: 24}
        - {component: C-05, service_ms: 1,  concurrency: 16, share: 0.9}   # попадание в кэш
        - {component: C-04, service_ms: 15, concurrency: 32, share: 0.1}   # промах
```

`share` — доля запросов сценария, доходящая до узла. `async: true` — узел не входит в задержку ответа пользователю (публикация в очередь), но нагрузка на него считается.

## 3. Нагрузочная проверка

`perf-agent` генерирует сценарии k6 **из предсказаний**, прогоняет и записывает измерения.

### Что обязательно в сценарии

1. **Прогрев** — кэши холодные при старте, первые секунды не считаются.
2. **Выход на целевой RPS ступенями**, а не сразу — иначе меряется поведение при шоке, а не при нагрузке.
3. **Удержание** целевого RPS не менее 5 минут — короткий прогон не покажет ни утечек, ни отставания репликации, ни накопления очередей.
4. **Поиск точки насыщения** — отдельный прогон с нарастающим RPS до отказа. Без него `saturation_rps` не проверен.
5. **Реалистичное распределение данных** — если в проде есть горячие ключи, они должны быть в тесте. **Равномерный синтетический трафик — главная причина, по которой нагрузочный тест проходит, а прод падает.**
6. **Пороги (thresholds) прямо из предсказания** — тест сам знает, что считать провалом.

### Формат результата

`reports/perf/<run-id>.json`:

```json
{
  "run_id": "req-orders-20260825",
  "commit": "a1b2c3d",
  "environment": "stage, 3 ноды app, 1 primary + 1 replica PG",
  "measurements": [
    {
      "prediction_id": "P-01",
      "scenario": "create_order",
      "achieved_rps": 580,
      "p50_ms": 45, "p95_ms": 420, "p99_ms": 1100,
      "errors_pct": 0.05,
      "saturation_rps": 940,
      "observed_bottleneck": "C-04 PostgreSQL — ожидание блокировок на orders",
      "duration_s": 300
    }
  ]
}
```

## 4. Калибровка

`scripts/check_capacity.py` (гейт G10) сверяет предсказания с измерениями и **накапливает журнал** `reports/calibration.jsonl` — по одной записи на каждую пару «предсказание — измерение».

Что даёт журнал: после десятка прогонов видно не «агент оценивает нагрузку», а конкретно — **где и в какую сторону он систематически ошибается**. Например: «задержку на путях с записью занижает в среднем в 2,7 раза; точку насыщения предсказывает в пределах 30%; хвост p99 занижает всегда».

**Архитектор обязан читать журнал калибровки перед новым предсказанием** и вносить поправку. Это и есть механизм, которым инструмент накапливает опыт.

### Что считается провалом гейта

- задержка или точка насыщения разошлись с предсказанием больше допустимого по `confidence`;
- узкое место оказалось не тем, которое предсказано, — **это важнее расхождения в числах**: значит, модель системы неверна;
- доля ошибок превысила `error_budget_pct`;
- сценарий из предсказаний не покрыт ни одним измерением;
- предсказание с `confidence: high` промахнулось.

### Чего гейт не требует

Прогон против прода. Стенд меньше прода — норма, при условии, что **окружение записано в отчёт**, а сравнение ведётся с поправкой на масштаб. Требуется честность про окружение, а не его полнота.

---

## 5. Как это чинит проверку нефункциональных требований

До этого цикла нефункциональные требования проверялись только глазами на ревью. G6 связывает критерий приёмки с юнит-тестом, но требование «p95 ≤ 300 мс при 500 rps» юнит-тестом не проверяется в принципе.

Теперь цепочка замыкается:

```
NFR-01 → предсказание P-01 → сценарий k6 → измерение → гейт G10
```

Каждое нефункциональное требование, поддающееся измерению, обязано иметь предсказание. Не поддающееся — идёт в секцию «Не верифицируется в этом прогоне» с причиной, как и раньше.
