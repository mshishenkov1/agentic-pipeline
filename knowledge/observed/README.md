# Наблюдаемые числа: ваша телеметрия вместо книжных ориентиров

**Уровень 2.** Справочник `03-числа-и-оценка.md` содержит общеотраслевые порядки величин. Они годятся для первой прикидки и бесполезны для точного проектирования: у вас своё железо, свои профили нагрузки, свои контракты на инфраструктуру, своё распределение по арендаторам.

Этот каталог — **источник истины, приоритетнее справочника**. Архитектор обязан использовать числа отсюда, если они есть, и общеотраслевые — только там, где ваших нет, отмечая это в обосновании.

Каталог наполняет **человек** из систем мониторинга. Агенты сюда не пишут (`knowledge/` в `protected`).

---

## Структура

```
knowledge/observed/
├── README.md              этот файл
├── latency.yaml           фактические задержки хранилищ, сети и сервисов
├── throughput.yaml        фактические пределы пропускной способности
├── traffic-profile.yaml   суточные и сезонные кривые, коэффициенты пика
├── distribution.yaml      распределение нагрузки по ключам и арендаторам
├── cost.yaml              стоимость единицы инфраструктуры по вашим контрактам
└── incidents.yaml         что уже ломалось и при каких условиях
```

Файл, которого нет, просто не используется — каталог наполняется постепенно.

## Форматы

### `latency.yaml`

```yaml
measured_at: 2026-08-20
source: "Grafana, прод, окно 30 суток"
storage:
  postgres_primary:
    point_read_p50_ms: 0.8
    point_read_p99_ms: 12
    write_commit_p50_ms: 3.2
    write_commit_p99_ms: 45          # хвост от fsync под нагрузкой
    note: "p99 записи ухудшается втрое в часы пик"
  redis_cluster:
    get_p50_ms: 0.4
    get_p99_ms: 2.1
network:
  same_dc_rtt_ms: 0.4
  dc_to_dc_rtt_ms: 12               # между вашими площадками
services:
  auth_service:
    p50_ms: 8
    p99_ms: 95
    note: "p99 определяется походом в LDAP"
```

### `throughput.yaml`

```yaml
measured_at: 2026-08-20
source: "нагрузочные прогоны, стенд равен проду"
limits:
  postgres_primary:
    read_rps: 18000
    write_tps: 2400                  # упирается в fsync, не в CPU
    max_connections_effective: 400   # выше — деградация из-за переключений контекста
    note: "измерено на текущем железе, NVMe"
  app_node:
    rps_per_node: 850
    cpu_cores: 4
    note: "при типовой бизнес-логике, без тяжёлой сериализации"
  kafka_broker:
    messages_per_sec: 240000
    mb_per_sec: 180
```

### `traffic-profile.yaml`

```yaml
measured_at: 2026-08-20
source: "аналитика, год наблюдений"
daily:
  peak_hours: "19:00–22:00 МСК"
  peak_to_average: 4.2               # НЕ книжные 2–5, а ваш факт
  night_to_average: 0.15
weekly:
  peak_day: "суббота"
  peak_to_average: 1.6
seasonal:
  - event: "чёрная пятница"
    peak_to_average: 11.5
    duration_hours: 8
    note: "в 2025 пик пришёлся на первые 40 минут"
  - event: "предновогодняя неделя"
    peak_to_average: 3.8
growth:
  yoy_users: 1.4
  yoy_data_volume: 2.1               # данные растут быстрее пользователей
```

### `distribution.yaml`

Самый ценный файл: именно он снимает риск горячих ключей, который в справочнике описан только как понятие.

```yaml
measured_at: 2026-08-20
tenants:
  count: 4200
  p50_load_share_pct: 0.008
  p99_load_share_pct: 0.9
  max_load_share_pct: 6.4            # крупнейший арендатор даёт 6,4% нагрузки
  note: "топ-20 арендаторов дают 38% трафика — шардирование по tenant_id даст перекос"
entities:
  - name: "карточка товара"
    top_1pct_share_of_reads: 0.44    # 1% товаров даёт 44% чтений
    note: "требуется отдельный кэш горячих карточек"
```

### `incidents.yaml`

```yaml
- date: 2026-03-14
  trigger: "рассылка push всем пользователям в 12:00"
  what_broke: "лавина одновременных заходов, пул соединений к PG исчерпан"
  blast_radius: "все пользователи, 22 минуты"
  root_cause: "нет джиттера в рассылке, нет backpressure на входе"
  architectural_lesson: "фоновые рассылки размазывать по времени; лимит соединений
                         к БД задавать явно и меньше, чем max_connections"
  now_checked_by: "чек-лист ревью, раздел «Ошибки эксплуатации»"
```

## Как агент этим пользуется

**`intake-agent`** — при сборе профиля нагрузки сверяется с `traffic-profile.yaml` и `distribution.yaml` и задаёт человеку предметный вопрос вместо общего: не «есть ли перекос по ключам?», а «по вашим данным топ-20 арендаторов дают 38% трафика — этот сервис наследует то же распределение?»

**`architect-agent`** — при расчёте нагрузки и выборе компонентов берёт числа отсюда. В обосновании обязан указать источник: наблюдаемое или справочное. Решение, опирающееся на справочное число при наличии наблюдаемого, — дефект, который ловит ревью.

**`perf-agent`** — воспроизводит в нагрузочных сценариях реальные перекосы из `distribution.yaml`, а не равномерный трафик.

## Статус наполнения

В новом проекте каталог пуст: файлы появляются по мере того, как человек
переносит сюда числа из мониторинга и нагрузочных прогонов.

**Что даёт даже частичное наполнение.** Один-единственный замер задержки под
растущей нагрузкой обычно даёт наблюдение, которого нет ни в одном справочнике:
медиана при росте RPS улучшается за счёт прогрева, а хвост p99 в это же время
растёт на порядок. Такое наблюдение нельзя взять из книги — только из своей
системы, и именно оно потом определяет, в каких терминах формулируются НФТ.

Каждый файл сопровождается пометкой, где он снят: прод, стенд или машина
разработчика. Замер на ноутбуке годится как нижняя граница и как демонстрация
формы хвоста, но не как основание для проектирования боевой системы.

## Регламент обновления

Числа стареют. Устаревшие числа хуже отсутствующих: они выглядят достоверно.

- поле `measured_at` обязательно в каждом файле;
- пересматривать не реже раза в квартал и после каждого значимого изменения инфраструктуры;
- архитектор обязан пометить в обосновании, если опирается на число старше шести месяцев;
- `incidents.yaml` пополняется после каждого разбора инцидента — это единственный механизм, которым конвейер накапливает опыт, недоступный из публичных источников.
