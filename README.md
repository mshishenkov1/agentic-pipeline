# Конвейер агентной разработки и тестирования в Claude Code

Замкнутый цикл `требования → код → тесты → баг-репорт → фикс → повтор → готовый код` внутри одной сессии Claude Code. Тест-агент — отдельный субагент с изолированным контекстом; найденные баги возвращаются dev-агенту через оркестратора в той же сессии.

## Архитектура

```
                 ┌─────────────────────────────┐
 требования ───► │  ORCHESTRATOR (гл. сессия)  │ ── state.json, маршрутизация,
                 └──┬──────┬──────┬──────┬─────┘    лимиты итераций, эскалации
                    │      │      │      │
              spec-agent dev-agent test-agent review-agent
              spec.md +  только    только tests/   свежий контекст,
              AC.yaml    src/      + bugs/BUG-*.json  approve/request_changes
                    ▲      ▲              │
                    │      └── BUG-*.json ┘   (фикс-цикл, лимит 3 итерации/баг)
```

Защита от подгонки: hook на каждую запись файла (зоны по ролям из `pipeline.config.yaml`) + diff-проверка `scripts/check_zone_diff.py` после каждого шага субагента. Полная трасса действий — `reports/trace/`.

Репозиторий содержит **только сам конвейер** — роли, хуки, гейты и базу знаний.
`src/` и `tests/` пусты: их наполняют агенты под ваш проект.

## Требования

**Инструменты проекта — Python ≥ 3.10** (`pyproject.toml`); в CI используется 3.12.
Они живут в `.venv` и запускаются явно: `.venv/bin/pytest`, `.venv/bin/mutmut`.

**Хуки и скрипты гейтов — Python ≥ 3.9.** Это отдельное требование, потому что
хуки в `.claude/settings.json` вызываются как `python3`, то есть берут
**системный** интерпретатор, а не тот, что в `.venv`. На macOS системный
`python3` — это 3.9, а отказ хука тих: страж зон записи просто перестаёт
срабатывать, и защита от подгонки исчезает незаметно. Поэтому `.claude/hooks/`
и `scripts/` намеренно держатся в границах 3.9: везде `from __future__ import
annotations`, никаких `match` и `X | Y` в вычисляемых позициях. Проверка:

```bash
python3 --version                      # системный интерпретатор, нужен ≥ 3.9
python3 scripts/run_gates.py           # должен отработать и напечатать G1–G14
```

Правя хуки или скрипты гейтов, держите эту границу — иначе конвейер потеряет
контроль зон на стоковой macOS.

## Быстрый старт

```bash
git clone https://github.com/mshishenkov1/agentic-pipeline.git my-project
cd my-project && rm -rf .git && git init
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
claude          # открыть Claude Code в этом каталоге
```

Конвейер работает от ветки `main`, поэтому нужен хотя бы один коммит:
`git add -A && git commit -m init`. Стек по умолчанию — Python; под другой язык
меняются `commands` и `zones` в `pipeline.config.yaml` (файл правит только человек).

Внутри сессии:

| Команда | Что делает |
|---|---|
| `/system-design <описание проекта>` | фаза системного дизайна: сбор требований + архитектура (один раз в начале) |
| `/design-change <что менять>` | изменение утверждённой архитектуры через новый ADR |
| `/pipeline examples/demo-requirements.md` | полный прогон конвейера |
| `/pipeline-status` | состояние из `state.json` |
| `/pipeline-resume` | продолжить после эскалации |
| `/bug BUG-001` | ручной фикс-цикл по багу |

## Фаза системного дизайна

Выполняется **один раз в начале проекта** командой `/system-design` и в обычный прогон не входит:

```
описание задачи ──► intake-agent ⇄ человек (раунды вопросов) ──► requirements.md   (REQ-NN, NFR-NN)
                         │
                         ▼
                    architect-agent ──► system-design.md + decisions/ADR-NNN.md
                         │
                         ▼
              дизайн-ревью ──► сводка оркестратора ──► апрув человека
```

Артефакты долгоживущие: прогоны `/pipeline` читают их, но не перегенерируют. Менять архитектуру позже можно только через `/design-change` — с новым ADR (старый вытесняется, а не переписывается) и апрувом человека. Проект без этой фазы работает как раньше: нет артефактов дизайна — гейты G7–G13 неприменимы.

Архитектор опирается на **базу знаний** `knowledge/system-design/`: процесс из девяти шагов, каталог из 14 НФТ, числа для оценки мощности, паттерны масштабирования и устойчивости (включая cell-based и shuffle sharding), ландшафт технологий, критерии выбора и триггеры ADR, обязательный комплект диаграмм, шаблон arc42, чек-лист ревью по шести столпам Well-Architected и разборы реальных архитектур (Discord, Figma, Slack, Uber, AWS). Результат подаётся человеку **пакетом ревью в виде Artifact** — с отрисованными диаграммами и обоснованием каждого решения.

## Quality Gates

G1 тесты 100% зелёные (skip — только с обоснованием) · G2 coverage-diff новых строк ≥ 90% · G3 mutation score ≥ 70% (mutmut) · G4 ruff + mypy чисто · G5 approve от review-agent · G6 каждый AC покрыт проходящим тестом · G7 каждое требование покрыто критерием приёмки или освобождено · G8 архитектура согласована с требованиями и кодом, ADR полны · G9 комплект диаграмм полон · G10 предсказания нагрузки подтверждены измерениями · G11 план миграции обратим · G12 инфраструктура без секретов и неразрешённых удалений · G13 контракты обратно совместимы · G14 слои тестов исполняются. Цепочка доказательств сквозная: `требование → критерий → тест` и `требование → компонент → модуль в src/`. G7–G14 условные: без соответствующих артефактов не блокируют. Прогон: `scripts/run_gates.py`; те же гейты независимо перепроверяет CI (`.github/workflows/gates.yml`).

                     test, review + 5 узких ревьюеров дизайна и redteam

                     /pipeline-resume, /bug
.claude/hooks/       контроль зон записи, guard bash, трасса, сброс агента
scripts/             state.py, check_zone_diff.py, changed_services.py,
                     check_ac_traceability.py, check_req_traceability.py,
                     check_design.py, check_diagrams.py, check_capacity.py,
                     check_migration.py, check_infra.py, check_contracts.py,
                     check_test_layers.py, simulate.py, run_gates.py
loadtests/           нагрузочные сценарии (роль perf)
knowledge/observed/  наблюдаемая телеметрия — приоритетнее справочных чисел
knowledge/system-design/  база знаний архитектора (только человек)

spec.md, acceptance-criteria.yaml, bugs/, disputes/, reports/, state.json — артефакты прогона

## Уровни автономности (внедрять постепенно)

`autonomy_level` в конфиге: **L0** — решения о мёрдже за человеком → **L1** — фикс-цикл замкнут, PR на ревью человеку (по умолчанию) → **L2** — review-agent обязательный гейт, человек смотрит эскалации → **L3** — автомёрдж вне защищённых путей (опционально). Автомёрдж в `main` не входит в объём конвейера.

## Безопасность

Только синтетические/анонимизированные данные; сетевой доступ — allow-list в конфиге; запрещены push в `main`, force-push, изменение `pipeline.config.yaml`, `.claude/`, `.github/` любым агентом; пороги гейтов меняет только человек.

## Известные ограничения

- Контроль зон привязан к `current_agent` в `state.json`, поэтому субагенты запускаются строго последовательно. В мультисервисном режиме это компенсируется сужением области: каждый прогон работает над одним сервисом.
- Мультисервисный режим включается `topology` в конфиге; топологию выбирает архитектор на этапе дизайна. Плоский режим остаётся умолчанием и работает как раньше.
- `guard_bash` — best-effort (редиректы/tee/sed); гарантию даёт diff-проверка после каждого шага.
- Запись в `state.json` разрешена всем хукам/скриптам конвейера; тампер ловится на ревью и в CI.
