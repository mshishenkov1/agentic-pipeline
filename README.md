# Конвейер агентной разработки в Claude Code

От пустого репозитория до проверенного кода за две фазы, обе — агентами, с человеком в точках решений.

**Фаза 1 — проектирование.** Агент собирает требования раундами вопросов, считает нагрузку, **сам предлагает язык и стек по каждому компоненту** и обосновывает выбор числами, выпускает архитектуру с диаграммами и ADR. Проверяют пять узких ревьюеров, red team и семь машинных гейтов.

**Фаза 2 — разработка.** Замкнутый цикл `спека → код → тесты → баг-репорт → фикс → ревью → гейты`. Тест-агент работает в изолированном контексте и не видит, как написан код; найденные баги возвращаются dev-агенту через оркестратора.

```
  описание проекта
        │
        ▼   ФАЗА 1 · /system-design ─ один раз в начале
  intake-agent ⇄ человек ──► requirements.md      REQ-NN, NFR-NN, профиль нагрузки
        │                                          «требование без числа — не требование»
        ▼
  architect-agent ─────────► system-design.md     карта компонентов C-NN, язык на каждый,
        │                    decisions/ADR-NNN     расчёт нагрузки, диаграммы, SLO,
        │                    contracts/, docs/     контракты OpenAPI/AsyncAPI
        ▼
  5 ревьюеров + red team ──► апрув человека
        │
        ▼   ФАЗА 2 · /pipeline ─ на каждое требование
  ┌─────────────────────────────┐
  │  ORCHESTRATOR (гл. сессия)  │ ── state.json, маршрутизация,
  └──┬──────┬──────┬──────┬─────┘    лимиты итераций, эскалации
     │      │      │      │
 spec-agent dev-agent test-agent review-agent
 spec.md +  только    только tests/    свежий контекст,
 AC.yaml    src/      + bugs/BUG-*.json approve/request_changes
     ▲      ▲              │
     │      └── BUG-*.json ┘   (фикс-цикл, лимит 3 итерации/баг)
```

Защита от подгонки: hook на каждую запись файла (зоны по ролям из `pipeline.config.yaml`) + diff-проверка `scripts/check_zone_diff.py` после каждого шага субагента. Полная трасса действий — `reports/trace/`.

Репозиторий содержит **только сам конвейер** — роли, хуки, гейты и базу знаний.
`src/` и `tests/` пусты: их наполняют агенты под ваш проект.

## Требования

**Инструменты проекта — Python ≥ 3.10** (`pyproject.toml`); в CI используется 3.12.
Они живут в `.venv` и запускаются явно: `.venv/bin/pytest`, `.venv/bin/mutmut`.

**Хуки и скрипты гейтов — Python ≥ 3.9.** Это отдельное требование, потому что
хуки в `.claude/settings.json` вызываются как `python3`, то есть берут
**системный** интерпретатор, а не тот, что в `.venv`. На macOS системный
`python3` — это 3.9, а отказ хука тих: страж зон записи просто перестаёт
срабатывать, и защита от подгонки исчезает незаметно. Поэтому `.claude/hooks/`
и `scripts/` намеренно держатся в границах 3.9: везде `from __future__ import
annotations`, никаких `match` и `X | Y` в вычисляемых позициях. Проверка:

```bash
python3 --version                      # системный интерпретатор, нужен ≥ 3.9
python3 scripts/run_gates.py           # должен отработать и напечатать G1–G14
```

Правя хуки или скрипты гейтов, держите эту границу — иначе конвейер потеряет
контроль зон на стоковой macOS.

## Быстрый старт

```bash
git clone https://github.com/mshishenkov1/agentic-pipeline.git my-project
cd my-project && rm -rf .git && git init
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
claude          # открыть Claude Code в этом каталоге
```

Конвейер работает от ветки `main`, поэтому нужен хотя бы один коммит:
`git add -A && git commit -m init`. Стек по умолчанию — Python; под другой язык
меняются `commands` и `zones` в `pipeline.config.yaml` (файл правит только человек).

Внутри сессии:

| Команда | Что делает |
|---|---|
| `/system-design <описание проекта>` | фаза системного дизайна: сбор требований + архитектура (один раз в начале) |
| `/design-change <что менять>` | изменение утверждённой архитектуры через новый ADR |
| `/design-reverse [путь]` | brownfield: зафиксировать архитектуру «как есть» перед проектированием перехода |
| `/pipeline examples/demo-requirements.md` | полный прогон конвейера |
| `/pipeline-status` | состояние из `state.json` |
| `/pipeline-resume` | продолжить после эскалации |
| `/bug BUG-001` | ручной фикс-цикл по багу |

## Фаза 1. Проектирование системы и выбор стека

Запускается командой `/system-design <описание проекта>` **один раз в начале** и в обычный прогон не входит. Артефакты долгоживущие: прогоны `/pipeline` читают их, но не перегенерируют. Менять архитектуру позже можно только через `/design-change` — с новым ADR (старый вытесняется, а не переписывается) и апрувом человека.

### Сбор требований — раундами, до чисел

`intake-agent` ведёт до четырёх раундов вопросов: контекст и границы → масштаб и нагрузка → качество и ограничения → платформа и организация. Правила жёсткие:

- **требование без числа — не требование**; каждое НФТ содержит величину, единицу и условия измерения;
- для времени отклика обязателен перцентиль: «среднее 200 мс» отклоняется, потому что ничего не говорит о доле пострадавших;
- каждый вопрос человеку обязан называть **конкретное архитектурное следствие** ответа — вопрос, для которого следствие не формулируется, не задаётся.

Выход — `requirements.md`: `REQ-NN`, `NFR-NN`, профиль нагрузки, платформенные ограничения, допущения и явный раздел «не верифицируется в этом прогоне».

### Проектирование — с расчётами и альтернативами

`architect-agent` не проектирует по памяти: перед работой обязан прочитать процесс, критерии решений, комплект диаграмм и правила выбора языка из базы знаний. Порядок работы:

- **Шаг 0 — платформа.** Восемь вопросов: где работает, сколько площадок, оркестрация, что переиспользуем, ограничения на технологии, команда, бюджет, регуляторика. Нет ответов — работа останавливается, а не подставляет умолчания молча: архитектура для управляемого облака и для закрытого контура различается принципиально.
- **Шаг 1 — слабые места спецификации** `W-NN`: что не так → на какое решение влияет → что нужно от человека. Критичный дефект — тот, при котором два разумных прочтения дают принципиально разные архитектуры; такой блокирует работу.
- **Шаг 2 — расчёты:** пиковый RPS, объём данных с индексами и репликами, трафик, **на какой ресурс упрёмся первым**, порядок стоимости. Без чисел решения считаются необоснованными, и ревью их отклоняет.
- **Минимум два варианта** по каждому существенному решению, сравнение по критериям со ссылкой на `NFR-NN` и посчитанные числа, и обязательная запись — **при каких условиях выбор был бы другим**.
- **Бюджет сложности:** по каждому компоненту проверка «если его убрать, какое конкретное требование перестанет выполняться?». Нет ответа — компонент лишний.
- **Запас 10×, а не гиперскейл сразу.** Обязательно закладывается: stateless-сервисы, отсутствие общей БД, идемпотентность мутирующих операций, версионированные контракты, ключ шардирования, сквозная трассировка и SLO, expand/contract для схемы.

Незаконные обоснования отклоняются на ревью: «быстрее», «современнее», «так делает Netflix», «на будущее», «это масштабируемо» без указания предела.

### Выбор языка и стека — обязанность агента

Компонент без языка и обоснования считается незавершённым проектированием, и гейт возвращает документ. Порядок критериев: **экспертиза команды перебивает всё**, кроме доказанной числами непригодности под профиль нагрузки; дальше экосистема под конкретную задачу, найм, эксплуатационная стоимость, совместимость с ландшафтом.

- умолчание — **один язык на систему**; второй вводится, только если есть компонент с профилем, для которого основной непригоден **по числам из собственного расчёта**, и у компонента чёткая граница по контракту;
- любой язык, отличный от основного, требует **ADR** с разобранной альтернативой «сделать на основном» и честной ценой;
- агент обязан назвать, **чем платим за каждый язык в самом конвейере**: какие нужны тесты, линтер, покрытие, мутационный инструмент — и какие гейты отключатся, если инструмента нет. Язык без работающего мутационного инструмента означает, что G3 по этому сервису не работает, и это говорится прямо, а не замалчивается.

Ландшафт технологий в базе знаний покрывает хранилища, обмен сообщениями, сеть и доставку трафика, оркестрацию, IaC, наблюдаемость, безопасность и нагрузочное тестирование — с практическими правилами выбора, а не списком модного.

### Что получается на выходе

`system-design.md` по структуре arc42, где карта компонентов читается машинно:

```markdown
### C-01: Название компонента
- **зона ответственности:** за что отвечает и за что НЕ отвечает
- **модуль:** src/<путь>
- **язык:** Go | Python | ...
- **обоснование языка:** со ссылкой на NFR и числа; чем платим в конвейере
- **требования:** REQ-01, NFR-02
- **зависит от:** C-02, C-05
- **состояние:** без состояния | состояние в C-NN
- **масштабирование:** как и до какого предела
```

Плюс комплект диаграмм в Mermaid (контекст C4 L1, контейнеры C4 L2, топология развёртывания, sequence на каждый ключевой сценарий с ветками ошибок, модель данных, матрица деградации), `decisions/ADR-NNN-*.md`, контракты OpenAPI/AsyncAPI в `contracts/` и `docs/slo.md` с SLI, SLO и бюджетом ошибок.

### Как это проверяется

Пять узких ревьюеров по очереди — масштабирование, данные, устойчивость, безопасность, стоимость; их противоречия (типично: стоимость против устойчивости) выносятся человеку. Затем `redteam-agent`, задача которого — **сломать дизайн, а не оценить его**. Затем машинные гейты G7–G13 и `scripts/simulate.py`, сверяющий предсказания нагрузки с измерениями. Итог подаётся человеку **пакетом ревью в виде Artifact** — с отрисованными диаграммами и обоснованием каждого решения — и без его апрува разработка не начинается.

### База знаний архитектора

`knowledge/system-design/` — 15 файлов, ~2500 строк: процесс из девяти шагов, каталог из 14 НФТ, числа для оценки мощности, паттерны масштабирования и устойчивости (включая cell-based и shuffle sharding), ландшафт технологий, критерии выбора и триггеры ADR, обязательный комплект диаграмм, шаблон arc42, чек-лист ревью по шести столпам Well-Architected, предсказание и проверка нагрузки, brownfield и миграции, выбор языка и стека, разборы реальных архитектур (Discord, Figma, Slack, Uber, AWS). Базу наполняет человек — агентам она закрыта на запись.

Проект без этой фазы работает как обычный конвейер разработки: нет артефактов дизайна — гейты G7–G13 неприменимы и не блокируют.

## Фаза 2. Замкнутый цикл разработки

`/pipeline <файл требований>` на каждое требование: `spec-agent` превращает его в `spec.md` и `acceptance-criteria.yaml`, `dev-agent` пишет только `src/`, `test-agent` — только `tests/` и баг-репорты `bugs/BUG-*.json`, фикс-цикл замыкается с лимитом 3 итерации на баг, `review-agent` со свежим контекстом выносит `approve` или `request_changes`, затем гейты. Если dev-агент считает тест неверным, он не правит его, а заводит спор в `disputes/` — разрешает ревьюер или человек.

## Quality Gates

G1 тесты 100% зелёные (skip — только с обоснованием) · G2 coverage-diff новых строк ≥ 90% · G3 mutation score ≥ 70% (mutmut) · G4 ruff + mypy чисто · G5 approve от review-agent · G6 каждый AC покрыт проходящим тестом · G7 каждое требование покрыто критерием приёмки или освобождено · G8 архитектура согласована с требованиями и кодом, ADR полны · G9 комплект диаграмм полон · G10 предсказания нагрузки подтверждены измерениями · G11 план миграции обратим · G12 инфраструктура без секретов и неразрешённых удалений · G13 контракты обратно совместимы · G14 слои тестов исполняются. Цепочка доказательств сквозная: `требование → критерий → тест` и `требование → компонент → модуль в src/`. G7–G14 условные: без соответствующих артефактов не блокируют. Прогон: `scripts/run_gates.py`; те же гейты независимо перепроверяет CI (`.github/workflows/gates.yml`).

```

                     /pipeline-status, /pipeline-resume, /bug

scripts/             state.py, check_zone_diff.py, changed_services.py,
                     check_ac_traceability.py, check_req_traceability.py,
                     check_design.py, check_diagrams.py, check_capacity.py,
                     check_migration.py, check_infra.py, check_contracts.py,
                     check_test_layers.py, simulate.py, run_gates.py
loadtests/           нагрузочные сценарии (роль perf)
knowledge/observed/  наблюдаемая телеметрия — приоритетнее справочных чисел
knowledge/system-design/  база знаний архитектора (только человек)

spec.md, acceptance-criteria.yaml, bugs/, disputes/, reports/, state.json — артефакты прогона

```

## Уровни автономности (внедрять постепенно)

`autonomy_level` в конфиге: **L0** — решения о мёрдже за человеком → **L1** — фикс-цикл замкнут, PR на ревью человеку (по умолчанию) → **L2** — review-agent обязательный гейт, человек смотрит эскалации → **L3** — автомёрдж вне защищённых путей (опционально). Автомёрдж в `main` не входит в объём конвейера.

## Безопасность

Только синтетические/анонимизированные данные; сетевой доступ — allow-list в конфиге; запрещены push в `main`, force-push, изменение `pipeline.config.yaml`, `.claude/`, `.github/` любым агентом; пороги гейтов меняет только человек.

## Известные ограничения

- Контроль зон привязан к `current_agent` в `state.json`, поэтому субагенты запускаются строго последовательно. В мультисервисном режиме это компенсируется сужением области: каждый прогон работает над одним сервисом.
- Мультисервисный режим включается `topology` в конфиге; топологию выбирает архитектор на этапе дизайна. Плоский режим остаётся умолчанием и работает как раньше.
- `guard_bash` — best-effort (редиректы/tee/sed); гарантию даёт diff-проверка после каждого шага.
- Запись в `state.json` разрешена всем хукам/скриптам конвейера; тампер ловится на ревью и в CI.
