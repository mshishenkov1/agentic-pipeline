Проведи фазу системного дизайна для: `$ARGUMENTS`.

Ты — ORCHESTRATOR (правила в CLAUDE.md обязательны). Фаза выполняется **один раз в начале проекта** и в обычный прогон `/pipeline` не входит. Её артефакты — `requirements.md`, `system-design.md`, `decisions/ADR-*.md`, `contracts/`, `docs/slo.md` — долгоживущие: дальнейшие прогоны читают их, но не перегенерируют. Изменение архитектуры позже — только через `/design-change`.

## 0. Предусловия

1. Прочитай секции `system_design` и `limits` из `pipeline.config.yaml`.
2. `state.json → system_design.status == "approved"` — фаза уже пройдена. Покажи артефакты и остановись: для правок есть `/design-change`.
3. Проверь, что база знаний на месте: `knowledge/system-design/00-INDEX.md`. Нет — останови и сообщи человеку.
4. Создай ветку `design/<слаг>-<дата>` от `main`.
5. `python3 scripts/state.py stage intake` и `python3 scripts/state.py design intake`.

## 1. INTAKE — сбор требований раундами

Субагент не может обратиться к человеку — вопросы задаёшь ты.

Повторяй, пока intake-agent не вернёт `status: "done"`, но не более `limits.max_intake_rounds` раундов:

1. `REV=$(git rev-parse HEAD)`; `python3 scripts/state.py agent intake`.
2. Вызови `intake-agent`: исходное описание + **все** ответы человека из предыдущих раундов дословно.
3. `python3 scripts/check_zone_diff.py intake --since $REV`. Ненулевой код — эскалация, остановка.
4. `needs_clarification` → `python3 scripts/state.py stage intake_questions`, задай каждый вопрос человеку через AskUserQuestion (варианты из ответа агента, всегда оставляй свободный ответ), затем следующий раунд.
5. Лимит исчерпан, вопросы остались → покажи их человеку и спроси: продолжать раунды или фиксировать остаток как явные допущения.

**Не переходи к архитектору, пока в финальном ответе intake не стоят `load_profile_complete: true` и `platform_answered: true`.** Без профиля нагрузки и без ответов о платформе архитектор всё равно вернёт задачу.

Результат: `requirements.md`. Проверь глазами сплошную нумерацию. Закоммить.

## 2. ARCHITECT — проектирование

1. `REV=$(git rev-parse HEAD)`; `python3 scripts/state.py agent architect`; `stage design`; `design design`.
2. Вызови `architect-agent`: вход — `requirements.md`. **Ответы человека из раундов intake не пересказывай** — всё существенное уже в требованиях, пересказ протаскивает случайные формулировки.
3. Если вернул `needs_platform_input` — задай вопросы человеку через AskUserQuestion, дополни `requirements.md` через intake-agent и повтори.
4. Если вернул `blocked_by_spec` с критичными `W-NN` — вынеси их человеку, получи ответы, дополни требования, повтори.
5. `python3 scripts/check_zone_diff.py architect --since $REV`. Ненулевой код — эскалация.
6. Результат: `system-design.md` с диаграммами, `decisions/ADR-*.md`, `contracts/`, `docs/slo.md`. Закоммить.

## 3. Машинные проверки и симуляция — ДО ревью

Не трать цикл ревью на то, что ловится скриптом:

```
python3 scripts/check_design.py
python3 scripts/check_diagrams.py
python3 scripts/check_req_traceability.py
.venv/bin/python scripts/simulate.py --sweep
```

**Симуляция обязательна, если в дизайне есть раздел «Модель нагрузки».** Она отвечает на вопрос «где насытится и при каком RPS» до постройки. Точка насыщения ниже целевой нагрузки или запас меньше ×2 — возвращай архитектору немедленно, ревью на таком дизайне бессмысленно.

Красное — верни архитектору с выводом скрипта. Только зелёное идёт дальше.

## 4. ДИЗАЙН-РЕВЬЮ: узкие специалисты

Один ревьюер не может быть экспертом по всем осям сразу. Пять специалистов смотрят каждый под своим углом, **строго последовательно** (контроль зон привязан к `current_agent`).

Не более `limits.max_design_review_cycles` циклов. В каждом цикле:

1. `python3 scripts/state.py agent review`; `design design_review`.
2. Прогони по очереди каждого из `system_design.specialist_reviewers`:
   `reviewer-scale`, `reviewer-data`, `reviewer-resilience`, `reviewer-security`, `reviewer-cost`.
   Каждому: свежий контекст, вход — `requirements.md`, `system-design.md`, `decisions/`, `contracts/`, `knowledge/observed/`. **Ход рассуждений архитектора не передавай никому.**
   Каждый пишет свой `reports/design-review-<ось>.json`.
3. `REV` фиксируй перед первым и проверяй zone-diff после последнего.
4. Собери находки всех пятерых. Дубли схлопни, противоречия между специалистами (типично: стоимость против устойчивости) вынеси отдельно — их разрешает человек по приоритету качественных целей из раздела 1 документа.
5. Есть `must_fix` → верни архитектору сводный список и повтори цикл.
6. Лимит исчерпан без чистого прохода → эскалация человеку со сводкой разногласий.

## 5. СОСТЯЗАТЕЛЬНАЯ ПРОВЕРКА (red team)

Чек-лист ловит то, что в него внесли. Этот шаг — про то, чего в списке нет.

1. `python3 scripts/state.py agent review`.
2. Вызови `redteam-agent`: задача — **сломать дизайн**, а не оценить его. Вход тот же, плюс `knowledge/observed/` (реальные распределения — лучшее оружие атакующего).
3. Результат — `reports/redteam-<n>.json` с атаками, ранжированными по произведению вероятности на последствие.
4. Атаки с `likelihood: high` и заметным последствием передай архитектору как обязательные к закрытию. Остальные — в раздел рисков документа.
5. Не более `limits.max_redteam_cycles` циклов.

**Атака, которую система не заметит, опаснее той, которую заметит сразу.** Если red team нашла пролом без сигнала в метриках — это находка и по устойчивости, и по наблюдаемости.

## 6. Проверка оркестратором

Прежде чем идти к человеку, сверь сам:

- каждое `REQ`/`NFR` находится в архитектуре либо в «Отложено» с причиной;
- нет компонента, не обоснованного требованием;
- расчёт нагрузки сходится с выбранными компонентами;
- у каждого существенного решения есть ADR с разобранной альтернативой и условием пересмотра;
- слабые места спецификации выписаны, критичные закрыты ответами человека;
- комплект диаграмм полон;
- раздел «Предсказания нагрузки» заполнен: у каждого измеримого NFR есть предсказание с `saturation_rps` и `bottleneck`;
- атаки red team с высокой вероятностью либо закрыты, либо приняты человеком как риск.

Расхождения возвращай архитектору, не человеку.

## 7. Пакет ревью для человека

Собери **Artifact** — так человек увидит схемы отрисованными, а не текстом Mermaid.

1. Сформируй `reports/design-review-packet.md`:
   - архитектура одним абзацем;
   - **все диаграммы из `system-design.md` как есть** (Mermaid в Artifact рендерится нативно), под каждой — что на ней и почему так;
   - таблица решений: решение → выбранный вариант → отвергнутая альтернатива → чем платим → при каких условиях пересмотрим;
   - оценка нагрузки и узкое место;
   - **результат симуляции:** точка насыщения и запас по каждому сценарию;
   - **сводка находок пяти специалистов** по осям (масштаб, данные, устойчивость, безопасность, стоимость) и противоречия между ними, если были;
   - **самые опасные атаки red team** и что с каждой сделано: закрыта, принята как риск, отложена;
   - слабые места спецификации и что с ними сделали; открытые риски и что отложено.
2. Опубликуй через Artifact с `file_path` этого файла, осмысленным `title` и `favicon`.
3. Дай человеку ссылку.

**Пакет — это объяснение, а не пересказ документа.** По каждому существенному решению должно быть видно: что выбрано, из чего выбирали, чем платим, когда пересматривать.

## 8. Апрув человека

При `system_design.approval == "human"` (умолчание):

1. Кратко назови главное: задача, ключевые NFR, архитектура абзацем, самые дорогие решения, открытые риски.
2. Спроси через AskUserQuestion: утвердить / вернуть на доработку с комментарием / отложить.
3. Утверждено → `python3 scripts/state.py design approved`, `stage idle`, закоммить, сообщи, что проект готов к прогонам `/pipeline`.

При `review_agent` достаточно вердикта ревью; при `none` апрув пропускается.

## 9. После постройки: замкнуть петлю измерений

Этот шаг выполняется **не в фазе дизайна, а после того как система построена** прогонами `/pipeline`. Напомни о нём человеку при утверждении.

1. `python3 scripts/state.py agent perf`.
2. Вызови `perf-agent`: сгенерировать сценарии k6 из предсказаний, прогнать, найти точку насыщения, записать `reports/perf/<run-id>.json`.
3. `python3 scripts/check_capacity.py` — гейт G10 сверяет предсказание с фактом и дописывает `reports/calibration.jsonl`.
4. Расхождение больше допустимого — это **не повод править предсказание**, а вход для архитектора: модель системы неверна, нужен разбор через `/design-change`.

**Журнал калибровки — то, чем инструмент накапливает опыт.** Архитектор обязан читать его перед следующим предсказанием.

## Чего в этой фазе не происходит

Ни строчки кода и ни одного теста. `dev-agent` и `test-agent` не вызываются. Реализация начинается отдельным прогоном `/pipeline`.
